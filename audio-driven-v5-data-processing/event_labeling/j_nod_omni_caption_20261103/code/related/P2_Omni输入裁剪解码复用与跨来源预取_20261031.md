# Omni 输入裁剪、解码复用与跨来源预取（2026-10-31）

用户授权实现三项输入侧优化。沿用既有 CPU 进程池、后台预取、就绪请求连续提交、跨机资源槽位和故障恢复机制。没有将旧 Qwen3-VL 的 batch512 直接套用于 Omni；Omni 保持已验证的单执行序列、最多提交 4 个已准备请求。

生产目录：`experiments/listen_j_omni_20261030/`；本次证据：其下 `input_speed_v1_20261031/`。部署状态及完整推理测速以该目录的验收记录为准。

## 三项实现

1. **像素一致裁剪**：`full_raw.prepare(..., fast_crop=True)` 复用 `frame_crop.crop_original_frame`，仍做原解码器 RGB 转换，先裁数组再构造 PIL 图像，省去构造高分辨率整帧 PIL 图像的开销。坐标、bicubic、JPEG85、8 fps 取帧与 PTS 校验不变。
2. **修正点头与 Omni 复用解码**：仅在变框且缺少可复用点头结果时，从同一次原视频解码取得原生帧率裁剪 RGB 和时间戳；Omni 沿用 8 fps 选择，点头沿用 25 fps 选择和原编码器／姿态模型。临时数组保存于执行主机 `/dev/shm/j-omni-shared-*`，来源、形状、像素哈希与递增时间戳经校验后读取，准备完成自动清理。已有点头缓存直接复用。**媒体预解码只占总解码槽位，完成后才申请点头槽位**，避免 10-bit 独立解码回退占用点头执行额度。
3. **跨来源预取**：每个 GPU worker 最多同时持有 4 个来源任务，保持原预取容量；按各来源待准备数分配任务，同来源优先较长片段，已准备完成的输入优先送推理。不必等当前来源最后一个慢片段结束才开始下一来源。每个片段仍使用其真实来源的点头结果、官方音频元数据与质量决定。

### 解码复用边界

Omni 环境为 PyAV17，冻结的点头环境为 PyAV16。实际视频验证发现，二者对 `yuv420p10le` 的 RGB 转换不同。因此仅对已核对的 **8-bit `yuv420p`** 共享 RGB；10-bit 或其他格式自动保留原独立解码。遇到帧格式变化，或点头声明时长与音频采样取整后的时长不完全一致，也放弃整段共享，避免边界帧差异。裁剪加速及跨来源预取仍可使用。

这避免为了加速改变点头模型输入。当前优化不覆盖所有视频的重复解码，不能将两条 8-bit 样本的收益当作全量收益。

## 正确性与恢复

- 保持新 J 切分、修正版 listener 框、官方词／句／VAD 并集净化音轨、pair 时间原点、8／25 fps、prompt 和模型解码参数。
- 已完成标签及原始输入不改写。旧框标签按此前约定保留实际来源；新结果继续记录 `original_source`、`source` 和 `crop_provenance`。
- 来源锁持有到该来源全部片段落盘；完成回执核对 caption／held／visual_excluded／visual_review 四个互斥终态。
- 异常与退出时先取消或排空 CPU futures，再释放来源锁。失败计入相应来源，成功输出在续跑时复用。
- GPU 进程读取配置后固定本进程优化选项，避免同一尝试中途改变输入路径。
- `preparation_metrics.fast_crop`、`shared_decode_used` 记录每条实际执行；`execution_revision` 增加 `+input-speed-v1+decode-before-nod-slot-v1`。调度指标不放入模型证据指纹。

## 配置与代码

配置位于生产 `config.json` 的 `input_optimization_profiles.<node>-gpu-<id>`：

```json
{"fast_crop": true, "shared_decode": true, "cross_source_prefetch": true, "max_sources": 4}
```

每卡准备进程／预取继续为 node17、node4 的 8／16，node8、node12 的 4／8；每机修正点头槽位 16、总解码槽位 112。跨来源不会乘大这些容量。

| 文件 | 职责 |
|---|---|
| `src/listen_benchmark/full_raw.py`、`frame_crop.py` | 保持像素的裁剪与可选原生帧输出 |
| `src/listen_benchmark/shared_visual_decode.py` | 临时 RGB、PTS、来源及哈希校验 |
| `scripts/listen_j_annotation_nod.py`、`listen_j_corrected_nod.py` | 在原点头路径读取共享帧 |
| `src/listen_benchmark/j_omni_crop.py`、`j_omni.py` | 修正版输入、按需共享及配置接入 |

## 已完成输入验收

80 项测试通过，包括实际帧格式与裁剪字节、8／10-bit 共享保护、跨来源就绪优先、所有者路由、失败计数、取消排空及来源锁释放，以及预解码不能占点头槽位、已有缓存不能重复准备。

6 条真实视频重放全部通过：原／优化 Omni 帧字节与元数据一致；点头中间视频 SHA256、姿态、得分、事件与参数一致。4 条变框、2 条不变框；4 条 10-bit 自动回退。

两个 8-bit 样本独立准备／共享准备耗时为 37.31／22.15 秒、61.30／41.86 秒。生产负载下的组件样本，不能当作整个流水线固定加速比例。证据：`input_speed_v1_20261031/shared_replay_guarded.json`。

完整推理验收采用 node12 GPU0、8 条固定输入、旧→新→新→旧顺序，逐项检查 prompt、画面、音频、输入 token 和生成结果；各阶段用独立临时点头缓存，避免前一阶段缓存命中造成虚假提速。检查失败自动退回旧输入路径，其他 GPU 继续生产。

初版实际结果：旧方案 148.51／129.54 秒，新方案 76.71／57.47 秒；合计 278.05→134.18 秒，吞吐比 **2.072 倍**，耗时降低 51.7%。8 条每轮均正常完成，模型输入字节、prompt token 与生成文本跨四轮完全相同。证据：`input_speed_v1_20261031/gpu_canary/complete.json`。这是同 GPU 小批量端到端对照，先于下述槽位调度修正；全量收益还取决于片段构成、来源尾部与点头缓存命中。

单卡进入正式生产后，实际结果的修正版来源、裁框、音频配方及点头来源校验通过，随后四机 32 卡分批滚动部署。**初版 2026-10-31 08:52 UTC 完成验收：32 个 worker 均恢复产出，心跳正常，无运行错误；当次抽查 19 条正式结果来源通过，任务队列失败为 0。** 首批三个来源已正常提交完成回执，终态数目吻合。

证据：`canary_production.json`、`canary_source_receipts.json`、`deployment_audit_initial.json`、`deployment_complete_initial.json`；固定参数快照 `deployment_config_initial.json`。这里的零失败指运行与任务提交，不表示模型的描述语义已经逐条人工确认。

### 生产窗口与槽位调度修正

初版切换前 40 秒窗口为 10.187 段/秒、平均 GPU 25.13%；切换后首个 40 秒窗口为 7.221 段/秒、GPU 19.37%；随后 60 秒窗口为 8.432 段/秒、GPU 19.46%。输入样本不同，且跨越重启，因此不构成受控对照；这些数据**没有证明全量已经提速**，不能用小样本 2.07 倍替代生产证据。

检查发现四机点头槽位均 16/16 占用，总解码槽位只占 13–18/112。初版把媒体预解码放在点头槽位内，10-bit 回退也会延长占槽时间。已将预解码移到点头槽位外，仍保留样本缓存锁和主机解码上限；点头编码／姿态计算继续受 16 槽限制。新增调度顺序测试通过，另重放 8-bit、10-bit 各一条，prompt、画面、音频与原生产输入均一致（`slot_order_media_check.json`）。

生产窗口原始记录位于 `nod_cpu_share/input_speed_before_20261031/`、`input_speed_after_20261031/`、`input_speed_after_warm_20261031/`；资源检查 `input_speed_v1_20261031/deployment_resource_limits.json`。后续修正版本以 `+decode-before-nod-slot-v1` 和最终部署验收记录识别。

**槽位修正版于 2026-10-31 09:09 UTC 完成四机 32 卡部署验收**：全部恢复正式产出，心跳正常，无运行错误、无失败来源；当次 16 条正式结果核对了修正版输入、音频配方、点头结果哈希及真实时间／裁框。记录为 `deployment_audit.json`、`deployment_complete.json` 和 `deployment_config.json`，初版记录另存 `_initial.json`，不覆盖历史结论。

修正版最后 60 秒生产窗口为 **8.099 段/秒、平均 GPU 利用率 20.71%**。node17／node8／node4／node12 分别为 1.567／3.083／1.567／1.883 段/秒，CPU 约 109／87／113／131 核。原始记录：`nod_cpu_share/input_speed_slot_order_final_20261031/`。

因此，本次结论是三项代码优化已实现、输入一致性与正式部署验收通过；**已有生产窗口尚未证明整体提速，也不能宣称 GPU 已满载或配置最优**。固定小批量 ABBA 收益与全量运行吞吐须分别引用。点头计算／输入准备仍存在供数限制，本次没有再次提高点头并发或改变模型推理参数。

## 操作与回退

本次参数先在单卡验证，再按批次滚动接入；只向已核对 PID、命令行和工作目录的本流水线 worker 发送正常退出信号，由既有守护重启。不得停止其他任务。

修改代码必须同步生产 `code_hashes`；工具为 `input_speed_v1_20261031/sync_hashes.py`。滚动工具为同目录 `roll.py`，检查新 revision 已存在时跳过。

回退某卡：在 `config-edit.lock` 下将该卡 `input_optimization_profiles` 设为 `{}`，再正常退出该 worker 并由守护重启；不可使用上述会跳过新 revision 的 rollout 工具充当回退。结果无需删除或重算，保留所有缓存与实际来源记录。

本次没有恢复 goal，也没有恢复周期汇报。

源码、测试、配置和验收材料的本地备份：`experiments/listen_j_omni_20261030/delivery_code/input_speed_v1_20261031/`，逐文件 SHA256 见其中 `MANIFEST.json`。未将媒体或结果树复制进代码快照。
