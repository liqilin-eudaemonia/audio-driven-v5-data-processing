# 四机32卡整体吞吐优化（2026-10-31）

目标是四机正式流水线的持续总产出。单卡小样本耗时、瞬时 GPU 利用率和代码部署成功都不能替代整体吞吐验收。

## 输入与结果不变

仍使用新 J 切分、画质前置筛查、已确认的修正版 listener 裁框、官方词／句／VAD 并集净化音轨、Omni 原生视频 8 fps、GLARE 25 fps 点头补充和原自然语言 prompt。模型、推理参数、重试规则、输出上限与准入规则均不改变。已完成结果按原来源保留，不重做或覆盖。

## 本轮定位与调整

1. 原先 8 条测试只有 5 个来源，每源 1–2 条；跨来源预取在这种小队列上收益大，不能代表正式来源每源几十至几百条的吞吐。
2. 点头并发 16／24 的生产 ABAB 窗口受时长、分辨率和裁框变化比例影响明显，不能仅根据某一窗口“段/秒”认定提速。
3. 8-bit 视频已能复用解码结果；10-bit 视频因 PyAV16／17 转色差异原先仍需重复解码。新增 **原始 YUV 平面传递**，由点头原运行环境执行自己的转色，避免混用不同 RGB 像素。
4. RGB 转换前用 FFmpeg crop filter 保留裁框外至少 32 像素上下文，起点按 32 对齐，保持色度与抖动相位；随后仍使用原 RGB 转换、PIL bicubic 512×512 和 JPEG85。滤镜保留全部 AVFrame 属性，特别是 PyAV 未暴露的 chroma_location。直接重建帧的早期实现未通过真实像素校验，未启用到生产。
5. 转色器按线程复用，显式单线程；crop filter 也限制单线程，减少大量 CPU 准备进程叠加时的线程开销。

YUV 临时内容只写本机 `/dev/shm`，每片段最多 4 GiB，消费后删除。超出预算或格式不支持时沿用独立解码，不删帧、不降帧率。没有新增永久 WAV、视频或训练缓存。

## 代码入口

- `src/listen_benchmark/frame_crop.py`：保留 AVFrame 属性的 YUV 裁切与原 RGB/PIL 转换。
- `src/listen_benchmark/shared_raw_decode.py`：有字节上限、来源绑定和 SHA256 校验的原始平面传递。
- `src/listen_benchmark/shared_visual_decode.py`：RGB／YUV 共享格式读取。
- `src/listen_benchmark/full_raw.py`：原采样规则、共享原始帧与兼容回退。
- `src/listen_benchmark/j_omni.py`：配置开关、执行版本及性能来源记录。

新增可选开关为 `input_optimization_profiles.<node>-gpu-<id>.roi_crop` 与 `shared_raw_decode`；默认关闭。启用后执行版本包含 `+raw-yuv-handoff-v1+roi-rgb-v1`。两项开关都只改变执行方式，不进入提示词。

## 校验和生产测量

证据目录：`experiments/listen_j_omni_20261030/global_throughput_20261031/`。

- `roi_parity.json`：6 条真实片段全部通过；包含 4K、10-bit、修正／未改变裁框。Omni 图像及元数据一致，点头视频 SHA256、姿态、得分、区间、模型与参数一致。
- `tests/test_roi_frame_crop.py`：图像边缘、奇数裁框起点、多种颜色参数、真实 H264 解码色度属性回归。
- `tests/test_shared_raw_decode.py`：原平面布局、颜色信息、来源、损坏检测与内存预算回退。
- `C_before_roi/`：正式32卡切换前180秒，**1948 条／10.821 段每秒**，GPU均值26.84%，无失败、无重启。时间戳读取边界使逐文件核对比worker计数多1条；精确视频时长约65.79秒每秒，按文件统计口径记录。
- `rollout.json`：分批切换记录。切换和模型加载耗时不计入稳定窗口，并单独留存。
- `run_window.py`：同时测4机固定worker计数、CPU/GPU、失败与PID；`exact_work.py`根据队列快照和已知来源核对真实完成的视频时长及源分辨率，不遍历全量结果树。

## 四机生产验收结果（10:22 UTC）

32卡均已实际产出；每卡独立核对一条新结果，共32条，修正版裁框、音频配方、点头来源与时间全部通过。两轮180秒窗口无worker重启、无新增生成失败，画质与caption失败队列均为空。四机远程进程身份与心跳检查通过。

| 指标 | 切换前180秒 | 第一轮180秒 | 第二轮180秒 |
|---|---:|---:|---:|
| 实际完成caption条数 | 1,948 | 3,670 | 3,239 |
| 四机合计，段/秒 | 10.821 | 20.379 | 17.994 |
| 处理视频时长，秒/秒 | 65.786 | 112.891 | 98.575 |
| 原始分辨率×视频时长，百万像素秒/秒 | 289.881 | 409.962 | 439.020 |
| GPU利用率均值 | 26.84% | 47.30% | 45.17% |

两轮合计6,909条，平均 **19.186段/秒**，比前置窗口高 **77.3%**；视频时长处理速度平均提高 **60.7%**。四台机器在两轮中均比各自前置窗口快：

| 主机 | 前置，段/秒 | 后两轮平均，段/秒 |
|---|---:|---:|
| node17 | 3.294 | 5.723 |
| node8 | 3.111 | 4.655 |
| node4 | 2.622 | 4.789 |
| node12 | 1.794 | 4.019 |

这是不同片段上的真实生产窗口，不是严格同样本的全量加速比保证；速度会随时长、分辨率、裁框变化比例和队列尾部波动。GPU均值仍低于满载，不能宣称全局最优。

补充的同样本输入准备ABBA：一条4K和一条10-bit输入，旧合计68.15秒、新合计53.71秒，约1.269倍；图像JPEG哈希、点头视频、姿态与事件一致。此数字只验证输入准备阶段，不能代替上表四机验收。

`acceptance.json`保存最终检查；`accepted_config.json`保存固定配置；`D1_after_roi/`、`D2_after_roi/`保存逐卡计数与完整核对。输入开关在全部32卡启用，点头并发24/机，其余已确认推理参数不变。准备进程仍为node17/node4每卡8个、node8/node12每卡4个，跨来源上限4。源级完成回执会等整源收齐才提交，不与逐条caption完成计数混用。画质、点头、Omni与故障恢复继续运行，未恢复goal，也未创建定时汇报。

代码、配置、测试与验收证据备份：`experiments/listen_j_omni_20261030/delivery_code/global_throughput_20261031/`，`MANIFEST.json`记录逐文件SHA256。

## 回退

在 `config-edit.lock` 下关闭上述两个可选开关，然后只对本流水线worker滚动重启。成功标注与正确点头缓存保持不动；原先的8-bit解码共享和独立10-bit路径仍可使用。不可因回退删除已完成数据。
