# P2 特征抽取：28卡配置与压测（2026-10-25）

部署资源为 node17（172.29.15.91）、node12（172.29.252.11）、node4（172.29.225.51）各 8 张 H200，加上 node8（172.29.104.220）GPU 4–7，共 28 卡。node8 GPU 0–3 不在本流水线授权集合中，调度和利用率统计均过滤到授权卡。

新增四卡已完成压测并接入原始视觉打标；原始 worker 完成并释放显存后自动接语义归属及原文整合，全量整合审计完成后接特征抽取。原始三支打标全部完成后才启动20分钟巡检计时，第一份新报告再等20分钟。已存在的历史试运行报告保留。

## 选择的配置

- 每卡 2 个常驻特征进程，每进程 2 个 CPU 线程，预取 2 段。
- 原生 input／teacher 的 CPU 解码与 processor 输入准备提前进入预取；GPU 运算、模型、prompt、特征定义与缓存身份保持原语义。
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，降低常驻多进程的显存碎片。
- `vae_workspace_slots=0`：额外 VAE 工作区串行化实验未优于最终配置，不启用。
- 原三节点各 32 个媒体准备进程，新增四卡节点 16 个；就绪任务水位 512，每任务 16 段。
- 每卡常驻进程上限为已验证的 2；峰值安全因子 1.05，额外留 16 GiB，OOM 时降并发。调速以有效吞吐为准。

## 压测结果

测试只占用 node8 GPU 4–7。使用 10 条真实媒体，重复组成每轮 40 个窗口；预热不计时，计时包含 input、teacher、VAE、events 与缓存写入。不同配置在空闲卡测量，结果不是全量数据速度承诺。

| 配置 | 段/秒/卡 | 说明 |
| --- | ---: | --- |
| 初始单进程，4 CPU线程 | 0.472 | 基线 |
| 双进程，2 CPU线程 | 0.630 | 未提前准备原生 input／teacher |
| 双进程，2 CPU线程，提前准备 | 0.785 | 尚未优化 CUDA 分配器 |
| 最终配置三次复测 | 0.772／0.767／0.760 | 平均 0.767，比基线快约 62% |
| 3进程＋VAE工作区限制 | 0.560 | 不采用 |
| 4进程＋VAE工作区限制 | 0.620 | 不采用 |

最终三次复测平均 GPU 利用率约 85.6%，混合样本显存峰值约 91.3 GiB。两个最大 305 帧形状同时运行，显存峰值 109.0 GiB，无 OOM。实际 GPU 利用率随媒体长度、CPU准备、写盘和尾批变化，不能承诺始终100%。

## 数值与部署验证

原生与优化路径在真实短／长样本的 input、teacher、VAE 上逐元素一致。最终配置另外对照10条样本的40份缓存，全部逐元素相同。共享文本缓存已生成并校验原生身份，生产 `CANARY.json` 已通过。8项CPU流程测试通过，包含“原始打标未结束不巡检”和“部分节点只使用指定GPU”。
