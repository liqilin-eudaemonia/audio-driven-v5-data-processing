# GLARE 大 microbatch 实测

2026-11-11，用户确认node11 GPU7有任务退出，要求重测128及更大的batch。有效batch256、FP16、lr峰值5e-4、reaction权重0.05。

## 结果与最终选择

- 128已跑通。两个长度175/299帧、256条真实样本交替32/128/128/32，计算暖机后32约3.41秒、128约2.19秒，128耗时减少约36%，峰值显存28.3GiB。见RESULT_128.json。
- 最长299帧的256条真实样本进一步测试128/192/256/192/128。192完成前后向，峰值39.5GiB。256达到约46.5GiB显存时触发测速进程45.95GiB额度，当时整卡剩余约1.9GiB。测试给同卡其他进程保留约2GiB余量，256的结果适用于当前共享GPU条件。见RESULT.json和probe_larger.log。
- 生产128观测27更新约2.43秒/更新，192观测35更新约2.49秒/更新。两者计算阶段均约2.0秒，差异主要出现在数据等待。不同样本和共享GPU负载影响前后测量，尚不能从这些数据认定相对原32的端到端收益。见PRODUCTION_COMPARISON.json。
- 最终采用128，192没有显示额外吞吐收益。训练继续，保存和完整dev验证每2000步。

此前并行测速时，vLLM显存占用增长使128触到约26GiB的进程额度。随后GLARE完成更新并保存，释放主训练显存，独立完成本次测试。其他进程继续运行。

## 当前代码及恢复

入口scripts/train_glare_paper_settings_v7.py，封装scripts/run_glare_paper_settings_v7.sh。准确参数与PID见原生产目录launch.json。

V7允许经过身份核对后切换microbatch，保存优化器、GradScaler、RNG、数据游标和epoch_order。每次切换保留当轮已经消耗的前缀，仅重新组织剩余长度桶。样本排列随分桶尺寸变化，训练成员保持完整。

新增data_wait_s和compute_update_s记录供数及计算更新耗时。每次安全切换的额外检查点用于恢复进度。此前0.2反应权重阶段与0.05阶段继续保留原始记录。
