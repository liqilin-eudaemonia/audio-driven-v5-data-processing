# 四机32卡巡检与自动恢复

已部署到 **node8和node17两个独立后台进程**，不依赖本次对话保持打开。当前容器没有cron，PID1也不是systemd，因此使用双机常驻守护；两机通过共享文件锁协调，同一时刻只执行一次恢复动作。

## 时间安排（北京时间）

- 每60秒检查一次四台机器、32个GPU和对应训练进程，确认步数持续推进。
- 每小时保存一份完整巡检记录到 `hourly/hour_XX.json`。观测暂时失败会保留记录并重试，不把SSH超时等同于训练停止。
- **11月2日02:38左右**开始专项检查仅AV接续。若AV＋Event仍健康运行，则继续等待它完成；若它已完成而仅AV没有正常运行，则自动拉起仅AV。
- 至少守护到 **11月2日08:47**；若两组尚未完成，守护继续运行到两组完成。

正常模型加载和保存需要时间，自动切换也有进程退出、显存释放和模型加载过程；守护负责防止无人处理的停训，不承诺这些必要步骤为零耗时。

## 恢复行为

进程缺失需要连续两次有效观测确认；步数不推进超过180秒后，再经下一次观测确认才执行恢复。新控制器或阶段启动有240秒加载宽限。恢复只终止本队列的控制器和训练进程，并校验PID、启动时间、完整命令身份，避免误杀或重复启动。

恢复时重新扫描完整检查点，核对文件SHA256；最新检查点损坏则回退到上一份完整检查点，不读取未完成写入的文件。AV＋Event继续原预算8,927步，完成后仅AV从独立初始化开始；仅AV中途失败则恢复自己的检查点。

正式运行保留134GiB单进程显存上限、隔层重算、每200步保存和TensorBoard。4小时检查不会中断仍在正常推进的第一组，也不会让两组抢占同一批32张卡。
