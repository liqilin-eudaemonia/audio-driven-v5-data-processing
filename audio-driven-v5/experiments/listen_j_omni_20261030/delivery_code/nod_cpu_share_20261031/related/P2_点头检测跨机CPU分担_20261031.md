# 点头检测跨机 CPU 分担（2026-10-31）

用户已授权：四机可用 CPU 优先处理剩余点头，保留画质筛查和 Omni 输入准备资源。本次为有界部署及测速，不恢复此前已暂停的 goal 或定时汇报。

## 实施设计

原 node17 点头工作进程继续运行，其他三机通过共享原任务队列协助。原 source claim 文件锁、原结果路径、原 source completion receipt 全部复用；辅助 slot 从 10000/20000/30000 起，避免与原 supervisor 冲突。辅助进程可恢复未完成任务，已有结果跳过。任务原归属不变。

入口 `scripts/listen_j_nod_cpu_share.py`。它调用原 `listen_j_annotation_nod.py`，仅将解码锁目录改为执行机器的资源目录，模型、25 fps、512 裁剪、recall 参数、画质准入和输出字段不变。辅助节点使用从 node8 已验证运行环境复制出的独立环境，避免 PyAV 版本差异。原运行环境不修改。

顺序仍为每个源任务先画质，再对保留片段提取点头，完成后交给现有 Omni 队列。不同源任务并行。音频净化仍在既有 Omni CPU 预取中执行，不新增音频文件。此次先消除跨机 CPU 分配不均，不修改整源完成回执的粒度。

比较过的方案：只增 node17 进程会争抢它的输入准备资源；迁移到 GPU 需重新验证检测数值；采用多机 CPU 分担能保持算法和媒体规格。用户已选择第三种调度方向。

## 部署和回退

运行记录：`experiments/listen_j_omni_20261030/nod_cpu_share/`。`config.json` 中逐机 workers 可热调；减少时只对本辅助进程发送 SIGTERM，当前片段结束后释放任务锁，其余进程续跑。`STOP` 或节点目录内 `STOP` 将辅助进程全部优雅退出，不停止原点头和 Omni。

每台机器的 supervisor 记录 PID/start_ticks，独占 supervisor.lock，子进程异常每小时最多重启三次。不要依据远程 PID 在本机判断存活；应在对应主机检查。

验收要求：跨机锁互斥、同输入点头输出一致、真实生产输出递增、无新增失败、原 GPU 进程身份不变、画质和 Omni 均持续前进。并发及测速结论以本目录部署记录为准。

## 本轮采用的资源配置

| 机器 | 处理剩余 node17 点头队列 | 专用画质进程 | Omni GPU | 每卡输入预取 CPU 进程 |
|---|---:|---:|---:|---:|
| node17 | 原有 48 | 32 | 8 | 8 |
| node8 | 辅助 48 | 32 | 8 | 4 |
| node4 | 辅助 32 | 48 | 8 | 8 |
| node12 | 辅助 40 | 48 | 8 | 4 |
| 合计 | 168 | 160 | 32 | 192（按需工作） |

node8 原来源队列的 80 个旧点头进程仍处于等待状态，不计入上表的 168 个有效队列处理进程。进程数不是 CPU 核数，也不等于持续占满；MediaPipe 原有内部线程设置未变。

node4、node12 专用画质池从 96 降为 48，通过逐机 PID/start_ticks 与命令核验后发送 SIGTERM，等已领取的源任务全部完成再重启 watchdog。未强杀画质任务，未重启任何 Omni GPU 进程。辅助点头任务仍先运行或复用同一套画质筛查。

## 已验证的证据

- `tests/test_j_nod_cpu_share.py`：4 项测试，覆盖解码资源目录重定向、主机与 slot 隔离、任务互斥与中断后的单次完成计数。
- `nod_cpu_share/lock_validation.json`：node12 持锁时，node8/node4/node17 均无法重复领取同一把锁。
- `nod_cpu_share/parity-{node8,node4,node12}.json`：同 3 条真实样本分别在三机重算，姿态、分数、事件、媒体及源信息逐字段一致，共 9 次对照。
- `nod_cpu_share/audit.json`：实际进程身份、生产输出递增、质量准入与来源抽查；不代表扫描了全部历史结果。
- `nod_cpu_share/{before,ramp1,steady1,final_window}/`：分机窗口速度及 CPU/GPU 采样。不同窗口的片段不同，属于生产运行观察，不能当成同样本严格加速比。
- `nod_cpu_share/worker_rate_end.json`：逐片段真实点头结果计数；队列的 `completed_clips` 则只统计整源完成回执，两者不可混用。

三分钟 `steady1` 窗口：点头队列完成回执约 7.37 段/秒，调整前一分钟约 2.03 段/秒；四机 Omni 约 11.22 段/秒，调整前约 11.96 段/秒。首轮预热窗口较慢，未据此继续盲目增加并发。最终验收后使用本配置，后续速度应按剩余样本重新估算。

## 读取与复用

原点头结果仍位于 `experiments/listen_j_annotation_node17_20261029/nod/results/`，原点头完成回执与 Omni 接续逻辑不变。消费者无需更改路径，也不能把辅助目录当成另一份标签数据。

在对应主机使用 `nod_cpu_share/runtime_env/bin/python scripts/listen_j_nod_cpu_share.py supervise --work experiments/listen_j_omni_20261030 --node node8`（其他机器替换 node 名称）；已经运行时独占锁会阻止重复 supervisor。正式启动命令和日志位置见各节点 `launch.json`。

辅助 supervisor 会恢复自身子进程的异常退出；它不是恢复整台机器、SSH 或自身进程的外部服务管理器。已暂停的 goal 和定时汇报没有重新开启。

最后120秒窗口：点头整源提交约6.63段/秒，Omni四机合计约10.00段/秒；CPU平均占用分别约135/123/118/138核（每机160核配额）。画质新池刚启动时整源提交会有延迟，不能将其短窗口回执率等同于持续测量速度。所有队列失败数为0，原32个GPU进程未重启。正式配置与全部窗口见 `nod_cpu_share/accepted_configuration.json`。
