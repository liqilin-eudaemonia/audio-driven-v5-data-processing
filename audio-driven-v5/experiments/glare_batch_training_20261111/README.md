# GLARE 反应权重0.05与真实批量训练

用户要求采用官方README反应损失权重0.05，并改善GPU7利用率。

## 实际改变

1. 从第181步开始reaction_loss_weight由0.2改为0.05；前180步及其checkpoint保留，不声称全程都是0.05。lr峰值5e-4、FP16、有效batch256不变。
2. 训练样本按精确帧数分桶，在桶内洗牌并随机排列批次，microbatch最多32。没有补帧、截断或删除短/长片段。当前迁移epoch保留已消耗的前缀，只重排未消耗样本；以后每epoch覆盖每个train成员一次。末尾不足256时接续下一epoch，与原循环相同。
3. 同一次更新的各微批损失按实际pair数加权。reaction有效mask按pair归一化，未知pair贡献0，避免人脸有效帧更多的pair被额外加权。批内随机参考时刻及条件dropout沿用官方原生forward，因此不能声称与旧逐pair执行随机轨迹等价。
4. 位置编码/mask缓存及每更新混合精度权重转换缓存保留。批量供数触发默认nofile1024限制，已仅在训练启动器提高至65536；失败发生在新更新开始前，从180步完整恢复。
5. 读取worker4→12未见明确额外收益，恢复4。新增按长度打包张量存储后进行进程间传输，解包为视图并保留原顺序，减少每批大量共享内存文件描述符及小对象搬运。

当前生产入口`train_glare_paper_settings_v4.py`／`run_glare_paper_settings_v4.sh`，参数、PID与权重仍在`../glare_paper_settings_node11_gpu7_20261111/`。

## 验证

- 3项单测：全部成员覆盖/可重现洗牌、迁移时已消耗前缀及剩余集合不变、不同有效mask下pair等权。
- 张量打包/解包CPU往返逐位一致、原顺序一致。
- 真实GPU前后向，256条覆盖不同长度的真实缓存，重复3次。逐条前向暖机后约4.4秒/更新；microbatch32约0.82秒/更新、峰值显存10.5GiB。该数字为缓存已在CPU内存中的计算短测，不含完整生产供数；见RESULT.json和benchmark_buckets.log。
- 生产microbatch32已运行，forward_calls通常9–10，而原版256；loss/梯度有限，没有FP16溢出。端到端结果与纯计算短测必须分开报告。

检查点仍每2000步保存；变更期间的额外保存仅为安全切换。按完整dev控制预算的规则未变。权重改变后重置旧最佳验证/早停计数，重新测量256条dev基线，避免比较两个不同目标函数的分数。

## 恢复

使用生产launch.json中的v4命令，不恢复旧v2/v3入口。Checkpoint包含epoch_order，恢复时完整重用该顺序和cursor，避免迁移epoch重排造成重复或遗漏。首次v3→v4只允许验证过的旧源码指纹，模型、优化器、scaler、RNG和数据成员均接续。
