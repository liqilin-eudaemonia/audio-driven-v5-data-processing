# 新数据规划LoRA：供数瓶颈定位（2026-11-02）

当前正式训练配置未改变，四机继续训练。本目录是有界CPU诊断和候选解码对照，不是已经部署的整机加速方案。

## 已有策略及本次遗漏

总索引原有[规划LoRA交接](../../../related/P2_Qwen回应规划LoRA_SFT代码准备_20261101.md)已明确：使用最终裁框首帧PNG缓存，每卡4个持久worker、时长分组、动态音频padding、BF16/SDPA/fused AdamW、关闭梯度重算、仅监督位置计算FP32 loss；旧500h第71—100步约0.6923秒/步。

新690337条接入保留了计算和组批设置，但从已缓存PNG改为原始视频按需解码，未保留同样的首帧供数速度。因此不能把旧步速或“最优配置”直接迁移到本次。SQLite引用索引解决清单扫描问题，不会消除视频解码成本。

## 实测

[输入profile](profile_inputs.log)：8条完整读取22.575秒，其中首帧21.659秒（约96%）；collator 0.143秒，来源校验/音频并非主要瓶颈。抽样训练日志平均约6.4秒/步，但部分步约0.6秒；有GPU utilization=100%同时带宽utilization接近0、功耗约120W的快照，符合等待/通信占用的表现，不能认为算力已用满。

| 独立对照 | 原读取 | 候选 | 核验 |
|---|---:|---:|---|
| 8条、缩短seek回退＋4线程SLICE | 21.625秒 | 9.525秒 | 8/8首帧RGB逐像素及PTS相同 |
| 8条、原seek＋4线程AUTO | 20.391秒 | 8.133秒 | 8/8逐像素及PTS相同 |
| 8条、原seek＋8线程AUTO | 20.391秒 | 5.481秒 | 8/8逐像素及PTS相同 |

对应[seek对照](decode_benchmark.json)、[AUTO对照](decode_auto_benchmark.json)，原始脚本和日志同目录。第二组采用原seek，没有叠加缩短seek，不能把两组加速倍数相乘。实验运行在训练并行期间、固定8条，并非随机顺序多轮ABBA；不能据此断言最优线程数或四机端到端收益。

部分长GOP样本因原先回退1秒而跨到前一个关键帧，需解码277／257帧；缩短回退后分别只需27／7帧，取到相同PTS和RGB。还有样本未减少解码帧数，AUTO多帧并行解码可降低该部分耗时。

## 后续应用边界

优先复用可验证的既有最终框首帧缓存，其余采用经过等价验证的解码或预准备。增加线程必须配合整机预算：32个数据worker每个8线程可超过单机160核配额，单样本快不代表整机快；4线程/worker更适合作为先验候选，仍需整机对照。

本次未改学习率、global batch、采样顺序、模型、源数据、目标标签或正在运行的reader。训练已有进度，切换实现应在完整检查点后保留模型、优化器、scheduler和32卡RNG，记录代码/读取协议变化，不能覆盖run.json来绕过恢复校验，也不能丢弃进度从头重跑冒充续训。
