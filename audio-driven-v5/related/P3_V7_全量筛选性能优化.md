## 具体处理步骤与硬件

| 阶段 | 工作 | 资源 |
|---|---|---|
| 原始目录清点 | TAR 成员清点、双人配对、participant/session 分组隔离 | CPU、共享存储；已完成 |
| 源数据检查 | 音视频与关键点长度、原视频方向和元数据 | CPU、ffprobe、原数据集关键点 |
| 话轮与自然切分 | 根据原转写和 VAD 跟踪 speaker/listener；实质插话排除；2–10 秒自然边界 | CPU |
| 裁框 | 最终子段固定裁框，原像素 ≥448，拒绝过宽/错误方向 | CPU、原数据集关键点 |
| 音量归一化 | 原参与者整轨测响度、固定增益、峰值限制、输出后测量和长度校验 | CPU、FFmpeg、共享存储；主要准备瓶颈 |
| 事件及声学分析 | 找有声事件、重采样、能量/频谱/瞬态特征 | CPU |
| AST | AudioSet 声音事件分类，提供语音、笑声等人声以及噪声证据 | GPU |
| PANNs Cnn14 | 独立声音事件证据；2 秒窗、1 秒步长覆盖全段背景 | GPU |
| 串音检测 | speaker/listener 双轨带通和局部时移相关性比较 | CPU |
| 分流与统计 | 人工区间反馈、keep/review/exclude、主池/开头备用池、2 秒/3 秒时长 | CPU、原子结果文件 |

两种模型为 `MIT/ast-finetuned-audioset-10-10-0.4593` 与 PANNs `Cnn14_mAP=0.431.pth`，均是音频事件分类模型，分别存于 `models/audio_qc_ast` 和 `models/audio_qc_panns`。转写、VAD、关键点直接使用原始数据集标注。本轮没有运行 LTX/Gemma/Bernini 训练，也未批量重编码视频或做复杂降噪。

speaker/listener 是随话轮变化的角色，源参与者音轨按 ID 匹配；识别到 listener 接管话轮后，下一段的条件音频和生成目标随之互换。真实输出核查见 `experiments/p3_listen_v7_validation/role_switch_example.json`。角色切换仍是自动规则判断，不能视为人工真值。

## 已确认的瓶颈和等价性验证

- 原配置：三机各 8 个模型进程，每进程仅 1 个 CPU 预取任务，按 rank 固定划分来源。实际总吞吐约 150–180 对会话/分钟，慢节点导致尾部等待。
- 单个真实会话的计划阶段约 0.65 秒，首次两轨响度处理约 10.63 秒。另一次测量中，12 个片段的完整音频 QC 共 2.75 秒；该样本不能代表全体，但表明准备阶段是明显瓶颈。
- 四对真实会话的冷归一化对照：串行 150.03 秒，4 并发 66.72 秒，CPU 准备约提速 2.25 倍。两种执行方式的完整 audit 完全相同，归一化 PCM 的 SHA256 和增益完全一致。
- 三机 24 线程共享目录测试：600 个任务无重复、无遗漏，三台实际分别领取 172/163/265 个任务。
- 证据：`experiments/p3_listen_v7_performance/baseline.json`、`screening_profile.txt`、`parallel_check/validation.json`、`shared_queue_check/validation.json`。

扩容入口：`scripts/scale_listen_v7_workers.py detach --group G --node N`，每个附加组增加每卡一个模型进程和每台 32 个准备槽位；组 1–5 在三台运行，组 6 仅在 node16 运行。需要降并发时使用 `drain --group G`，该组停止领取新任务并完成已领取任务；不能直接 kill 并丢下已领取任务。

**不要同时重启旧静态分片入口。** 动态队列的任务领用状态单独持久化；异常中断恢复前要核对已领取但尚未产生结果的任务，不能只按队列 cursor 推断全部完成。

## 监控与结束条件

- `scripts/monitor_listen_v7_resources.py`：每台每 15 秒采集允许 CPU 范围的利用率、I/O 等待、GPU 利用率与显存、模型进程数、完成量；默认运行最多一小时，任务完成可提前退出。
- `scheduling_v2/telemetry/node_*.jsonl`：持续监控记录；`node_*.json` 为最新快照。
- `scheduling_v2/extra_groups/group_*_node_*.json`：附加进程组的状态和退出码。
- `screening_summary.json`：唯一数据量统计入口。报告器等待基础组和所有附加组都结束，再导出完整来源清单；暂存的 finalization hold 用于扩容注册期间，不能留作永久阻塞。

并发不会降低 448 裁框、放宽音质阈值或改变 backchannel 分池。资源利用率用于诊断，以实际完成吞吐、错误率和输出一致性决定配置。
