# 原生视频 8 fps 打标加速实测与推荐配置

2026-10-29，node17（172.29.15.91），8 张 H200。用户要求尽量提高速度，并在途中明确取消小 batch／低 token 预算测试；之后明确授权与 pair 处理任务叠加。本轮没有终止其他任务，没有启动全量重打标，也没有替换已有训练标签。

## 当前结论

**已完成测试中最快的是 batch 256＋16384 token 调度预算＋50 个片段共同组批。** 同一 GPU 处理 50 条／293 个完整和滑窗请求，准备好的帧输入下耗时 84.655 秒，约 0.591 段/秒。这个时间包含读取帧缓存、构建请求、推理及检查点写入，**不包含源视频解码建缓存和模型初始化**；不能据此直接估计全量从原始 TAR 开始的完成时间，也不能直接乘 8 宣称已经测得整机吞吐。

| 请求批量上限 | token 调度预算 | 每组片段 | 50 条处理时间（秒） | 段/秒 |
|---:|---:|---:|---:|---:|
| 64 | 32768 | 16 | 128.22 | 0.390 |
| 64 | 65536 | 16 | 128.07 | 0.390 |
| 128 | 16384 | 32 | 101.88 | 0.491 |
| 128 | 32768 | 32 | 98.12 | 0.510 |
| 128 | 65536 | 32 | 107.46 | 0.465 |
| **256** | **16384** | **50** | **84.66** | **0.591** |
| 256 | 32768 | 50 | 88.12 | 0.567 |
| 256 | 65536 | 50 | 87.78 | 0.570 |

每组在一张卡上跑同一份 50 条样本，8 组并行。相对该表最快的 batch64 配置，最佳组耗时减少约 33.9%，吞吐提高约 51.3%。各组同时改变了请求队列和片段组大小，不能把收益全部归因于一个 batch 数字。256 是提交上限，vLLM 仍按实际 token／KV 空间调度；不代表始终有 256 个请求同时计算。本次最佳组实际提交两批：256 和 37 个请求。

本轮不是稳定独占资源的重复对照：另一项 pair 任务的负载和调度状态发生过变化。测试结束后再次申请重复测试及 batch512 对照时，部分卡仅余约 21–28 GB，显存检查阻止了启动。因此目前称为**已完成配置中的最快方案**，不是全局最优；这些后续对照没有结果。

## 输入和输出核对

- 模型仍是 `/private/ckpts/Qwen3-VL-8B-Instruct`；C prompt、512×512 listener 原裁框、8 fps、JPEG85、原始 PTS、整段＋3 秒／1 秒滑窗、4096 输出 token 上限不变。
- 最佳组全部 293 个请求的 prompt、video metadata、窗口时间、原始帧证据及输入 token 数与历史 video8 相同。
- 所有 8 组均 50/50 整段通过；请求为 284/293 通过，零截断。最佳组未通过的 9 个窗口与历史是同一组窗口；原响应继续保存，不擅自修改边界。
- 最佳组有 160/293 条原始响应与历史逐字相同。历史事件总数 1231，最佳组 1245，含无效窗口中的候选事件。批量改变后存在措辞、区间和动作描述差异；数量接近不等于准确率相同，本轮没有新增人工真值或证明内容完全等价。
- 最佳组 GPU 推理期间按约 10 秒采样，利用率平均约 76.8%、峰值 100%；该卡整个监控窗口显存峰值约 71.0 GiB。统计受其他任务和采样粒度影响，不能解释为模型独占占用。

## 加速代码

- [运行入口](../scripts/listen_visual_native8_nod.py)：新增跨片段组批入口、解码槽位、可选组内 CPU 解码线程，以及执行参数和源码哈希记录。
- [跨片段批处理](../src/listen_benchmark/visual_batch.py)：多个片段共同提供窗口请求，每个请求保留独立 schema、时间与来源；每批按片段分别落断点，不混写来源。重启补齐未保存窗口。
- [负载均衡与预取](../src/listen_benchmark/visual_schedule.py)：按工作量分卡、有界预取、异常传播。
- [原样帧缓存](../src/listen_benchmark/visual_media_cache.py)：缓存原解码器输出的 PIL RGB 帧和元数据，没有换成另一个视频或采样率。键包含源记录、源 archive 大小/mtime 和解码代码哈希。本机可信 pickle，禁止从不可信来源加载。
- [8 卡测试入口](../scripts/benchmark_listen_visual_native8.py)：独立输出目录、资源采样、显存检查、任务退出清理；共享 GPU 必须显式 `--allow-shared`。不同测试目录共用解码锁，避免各自增加一组读进程。
- [结果分析](../scripts/analyze_listen_native8_benchmark.py)：输入一致性、原始输出差异、请求通过率与吞吐汇总。
- [CPU 回归](../tests/test_visual_annotation_schedule.py)：13 项已通过，包含跨片段来源与失败续跑、缓存失效和输入内容保留。组内并行解码参数已实现，尚未完成其原视频 GPU 端到端测速。

## 使用已测配置

[机器可读配置](../configs/listen_visual_native8_node17_throughput_v1.json)记录实测参数；当前 CLI 不自动载入该文件，下列命令显式指定相同值：

```bash
CUDA_VISIBLE_DEVICES=0 \
LD_PRELOAD=/private/software/conda/envs/vllm/lib/libstdc++.so.6 \
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=1 \
/private/software/conda/envs/vllm/bin/python scripts/listen_visual_native8_nod.py vlm \
  --manifest /absolute/path/source_samples.json \
  --output /absolute/path/new_run/visual8 \
  --rank 0 --shards 8 \
  --batch-size 256 --max-num-batched-tokens 16384 \
  --batch-frame-budget 8192 --clip-batch-size 50 \
  --prefetch 1 --scheduling balanced --memory .45 \
  --decode-slots 4 --decode-workers 1
```

其余 7 个 worker 分别使用 GPU/rank 1–7；完整 manifest、shards、输出目录和执行参数保持一致。显存 .45 是本次实测预算，不保证在其他任务已占据大部分显存时仍能启动。改变参数或代码应新建输出目录，不能直接混入历史协议。

上述命令默认从原视频读取，**没有预建帧缓存，不能承诺表中速度**。重复小样本测试可加 `--prepared-media-cache /dev/shm/listen_native8_speed_20261029`；该目录属于 node17 的临时帧缓存，其他机器不共享。不要将整套百万片段数据无界写入该缓存。全量只遍历一次时，应优先验证并行解码与推理重叠；代码支持 `--decode-workers` 和主机总 `--decode-slots`，目前不把未测的更高并发推荐为最优值。

缓存构建成本：首批 16 条约 49.0 秒；扩展到 50 条又花约 161.8 秒，其中 16 条命中、34 条新解码，后台负载不同。此成本没有计入表格。
