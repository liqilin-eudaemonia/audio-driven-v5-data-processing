# 评测CPU预取与像素计算流水化提速

适用范围：已有生成视频的配对指标评分，使用既有 ResponseNet／Seamless 评测协议。优化视频读取、CPU像素指标和GPU网络评分之间的等待；不修改生成、音频评分或指标定义。

## 1. 原瓶颈与处理方式

原进程按“读取当前视频 → CPU逐帧PSNR／SSIM → GPU LPIPS／FID／FVD／人脸／表情”串行执行。增加评分进程能交错部分计算，但单进程内部仍有等待。

新增有界CPU准备队列：一个后台读取线程依次调用**原生 `load_pair`**，常驻4线程池调用**原生 `pixel_scores`**，提前准备后续样本。主线程保持原顺序运行GPU模型。后台不访问GPU，不预取其他清单或修改图像。

主线程取得当前帧数组后，像素阶段直接取已算好的逐帧结果；代码核对数组地址、shape、strides和dtype，遇到不属于当前样本的帧明确报错。解码失败按原流程报pair错误，像素失败仍在像素阶段报错，其余样本继续。退出时取消未开始的任务、等待正在执行的CPU任务并关闭线程池。

| 配置 | 本次验证设置 |
|---|---|
| CPU预取深度 | 2，最多2个准备中的／已准备的后续任务，加当前样本 |
| 后台视频读取 | 1线程，使用原解码函数 |
| 后台PSNR／SSIM | 常驻4线程，原公式和原帧顺序 |
| LPIPS／FID batch | 64，保持历史配置 |
| 人脸／表情 | 原CUDA后端，原权重和处理 |
| GT复用 | 原无损解码缓存＋原特征缓存 |
| 正式评分并发 | node11单卡已验证8个原生评分进程；新流水线的同样本测速为单评分进程，尚未证明其与8路并发组合的全量提速倍数 |

预取深度不是GPU batch。视频长度、分辨率和进程数增加时，要同时考虑CPU与内存；不能将单进程测速倍数乘以进程数作为全量速度。

## 2. 数值与缓存约束

- 不修改 `OmniResponse/evaluation/video/paired_metrics/` 的原评分源码；使用独立执行包装入口。原生代码、权重及GT缓存身份保持，新执行代码的SHA单独记入contract。
- 帧像素、裁框、FPS、帧序、有效支持、FID/FVD抽帧、数据类型、VAE与音轨均不变。
- 不把PSNR／SSIM移到另一套GPU近似实现；逐帧仍调用同一个CPU函数。
- 不改变全量FID/FVD的汇总方式，仍合并全部样本特征后计算，不能平均分片分数。
- `cpu_pipeline.json`记录后台读取时间、像素计算时间和主线程等待时间。原生逐条`timings.decode/pixels`在流水线模式下主要反映等待／取结果时间，不能再作为后台CPU实际耗时。
- 音频评分命令保持原样，静音／短回应／UTMOS N/A规则不变。

## 4. 运行方式

从项目根目录运行；下面以仅授权的node11物理GPU7为例。

```bash
CUDA_VISIBLE_DEVICES=7 OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=2 \
  /private/software/conda/envs/AnyTalker/bin/python \
  scripts/p2_pipelined_video_metrics.py \
  --prefetch-depth 2 \
  --manifest /absolute/path/pairs.jsonl \
  --output /absolute/path/new_score_output \
  --assets /private/liqi_workspace/project_code/OmniResponse/evaluation/video/paired_metrics/assets.local.json \
  --device cuda:0 --face-device cuda:0 --emotion-device cuda:0 \
  --threads 4 --pixel-workers 4 --batch-size 64 \
  --face-padding 0 --gt-cache /absolute/path/existing_gt_feature_cache \
  --feature-output /absolute/path/new_score_output/features.npz \
  --allow-partial
```

Seamless可另加 `--decoded-gt-cache /absolute/path/existing_decoded_gt_cache`。ResponseNet沿用原 `--face-padding 64`；不能把示例中的0用于ResponseNet。其余采样参数以既有protocol为准。

在**新的、未运行的评测队列**使用原protocol并选择新入口：

```bash
CUDA_VISIBLE_DEVICES=7 OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=2 \
  /private/software/conda/envs/AnyTalker/bin/python \
  scripts/p2_pipelined_testsets_eval.py metrics_queue \
  --work /absolute/path/evaluation_work
```

先核对该work的 `cluster`、`metrics_cluster`、允许卡号、评分并发及 `SMOKE_COMPLETE.json`／生成与绑定完成状态；CLI上的GPU7不会替代远程调度的cluster授权。队列通过同一新入口启动评分worker，既有锁、成功标记、失败重试与合并沿用原逻辑。勿与活跃的旧评分控制器重复启动；历史完成目录无需重跑。要回到原执行方式，对新队列使用原 `scripts/p2_testsets_eval.py metrics_queue` 即可。

## 5. 真实验证与保存位置

使用本轮step6500已经生成的真实视频，按时长覆盖短／中／长片段，每套4条，共8条；两个模式各跑同一份清单。Seamless先原生后流水线，ResponseNet反向运行，减少固定顺序影响，但不是完整ABBA或全量并发基准。

原始数据与结果位于 [p2_metrics_cpu_pipeline_20261107](../experiments/p2_metrics_cpu_pipeline_20261107/)。`RESULTS.json`为最终速度与精确一致性报告；`STATUS.json`记录完成状态；`unit_tests.log`为7项测试。代码快照及 `CODE_SHA256.json`同目录保存。

最终报告 `RESULTS.json` 已通过：

| 测试集（同4条视频） | 原串行总耗时 | 流水线总耗时 | 总耗时缩短 | 吞吐倍数 |
|---|---:|---:|---:|---:|
| Seamless | 59.20秒 | 35.65秒 | 39.77% | 1.66× |
| ResponseNet | 78.03秒 | 55.45秒 | 28.94% | 1.41× |

上表包含各进程初始化；仅逐条评分循环，Seamless为44.92→23.02秒，ResponseNet为67.21→42.80秒。流水线主线程等待输入累计分别为0.00026秒、6.70秒，实际CPU读取／像素计算时间另存报告，未把隐藏的后台计算算成消失。

8条真实样本逐条指标、像素统计、人脸覆盖、情绪及动作结果、FID/FVD特征数组、最终汇总和覆盖均完全一致；GT特征缓存命中状态及代码／权重身份一致。Seamless有1条原有表情／动作支持不足，两种模式保持相同，未当作新增错误。7项单元测试全部通过。

这是单进程、8条真实视频的有限对照；两套测试集使用相反模式顺序。没有宣称已完成8路并发组合测速或获得全量最优配置。
