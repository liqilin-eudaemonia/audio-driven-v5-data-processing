## VITA-1.5 的训练方案

依据本地 [VITA-1.5.pdf](VITA-1.5.pdf) §3.3、图3，第5—7页。

| 阶段 | 目标和数据 | 更新范围 |
| --- | --- | --- |
| 1.1 视觉对齐 | 20% caption 数据，视觉输入→描述 | 视觉Adapter；视觉编码器和LLM冻结 |
| 1.2 视觉理解 | 全部caption数据，视觉输入→描述 | 视觉编码器、Adapter、LLM |
| 1.3 视觉SFT | 全部QA＋20% caption，视觉及问题→文字回答 | 视觉编码器、Adapter、LLM |
| 2.1 音频对齐 | 先用CTC训练语音编码器，再以语音→转写对齐LLM | 后一步LLM冻结，语音编码器、Adapter及任务引导token可训练（图3） |
| 2.2 音频SFT | 抽取4% caption、20% QA；约一半文字问题由TTS转成语音，回答仍为文字 | 视觉／语音编码器及Adapter、LLM；另有输入模态State Head |
| 3.1 Codec | 语音编码为离散token并重建 | Codec编码器和解码器 |
| 3.2 语音输出 | 约3000小时文本—语音，文本embedding→NAR→AR→语音token | NAR／AR解码器；LLM冻结 |

数据比例是对原数据类别的抽样比例，不是最终混合数据的占比。论文§3.2写110,000小时ASR数据，§3.3.2及图3写11,000小时，存在口径不一致，不据此确定我们的预算。

1.3／2.2的文本监督可由官方代码确认：完整对话按因果注意力执行teacher forcing，用前文预测下一个token；用户指令及多模态占位对应位置使用忽略标签，回答及相应控制token参与交叉熵。训练无需先自由生成再对整段文字打分。推理才自回归生成。

官方参考：[文本交叉熵](https://github.com/VITA-MLLM/VITA/blob/main/vita/model/language_model/vita_qwen2.py)、[数据标签](https://github.com/VITA-MLLM/VITA/blob/main/vita/util/data_utils_video_audio_neg_patch.py)、[多模态序列](https://github.com/VITA-MLLM/VITA/blob/main/vita/model/vita_arch.py)。官方公开续训脚本为1轮、LR=1e-5、3% warmup、cosine，但冻结语音编码器；这不是论文两个阶段完整原配方。论文未给出State Head损失权重。

## 我们的初步方案及边界

当前 guided S1 用目标listener自然语言描述训练双通路音视频生成，先学习执行行为指导。原代码S2通过AV＋Event更新Qwen条件hidden，并没有描述token交叉熵，不能直接当作描述生成SFT。

候选后续步骤：

1. 首先测试**未微调**Qwen-Omni-3B，仅凭speaker音频＋listener参考图能否自由生成合理回应规划。
2. 若规划能力不足，再训练描述生成LoRA：上述输入＋固定规划指令，现有listener自然语言描述作为assistant目标，回答token交叉熵；先不接AV损失。只训练LoRA是我们的资源选择，并非VITA论文的全模块更新设置。
3. 将预测描述同时送入Qwen条件分支与Gemma，结合现有S1评估实际AV效果；与真实描述条件分开记录。
4. 只有发现生成侧不适应预测描述，再考虑预测描述条件下的AV＋Event适配。不能预先断言必须新增完整训练轮次。

VITA的3.2采用配对文本训练输出模块，没有声明必须用LLM自由生成文本训练。因此此前“必须用实际预测描述再训练”的说法过强，应先评测再决定。预测文本是离散结果，普通AV反传不会穿过生成token直接训练前面的规划过程。

我们的回应具有一对多性质：标注描述是一种真实反应，不是给定speaker语音时唯一正确的计划。评审应检查角色、语义／语气适配、可执行动作、沉默／短促附和是否合理，不将逐字符合标注当成合理性的定义。最终主要看仅音频＋参考图输入的音视频效果。

## 未微调3B：原24条复核样本试验

用户指定原 [24条清单](../experiments/listen_j_face224_training_review_20261101/review_sample_list.csv)，20 train＋4 dev；本次仅推理，不把dev加入训练。模型为原始 `/public/2_CKPT/3_PreTRAINED/Qwen2.5-Omni-3B`，无LoRA。

输入采用已验收的最终裁框参考PNG与对应speaker原始float32波形，重采样到16kHz，与训练输入的重采样方法一致。明确system＋user，输出自然语言段落，不强制JSON或时间区间。不输入listener音轨、后续帧、转写、标注描述、事件统计或静音标签。speaker转写及原标注仅在生成后供人工审阅。

资源：`172.29.189.119:22`，主机 `dedicated-developjob-js-infer-machine-ws3qe`，物理GPU7。首次实测GPU7已有约64GiB占用、100%利用率，约76GiB剩余，并非完全空卡；使用剩余容量批量推理，不终止其他任务。

完整prompt、输入哈希、解码设置、原始输出及检查结果保存到 [试验目录](../experiments/p2_j_omni3b_autonomous24_20261101/)。本轮不启动音视频生成，不据文本规划结果宣称AV质量改善。

### 运行结果与复现

已完成24／24，全部正常EOS结束，输出14—64 token，共575 token。原生Thinker文本生成，BF16、SDPA、KV cache、left padding；24条一次合批，greedy，最多512新token，未按质量重试或挑选。视觉输入最大50,176像素。完整system/user见 [protocol.json](../experiments/p2_j_omni3b_autonomous24_20261101/protocol.json)，逐样本完整聊天输入见 [requests.json](../experiments/p2_j_omni3b_autonomous24_20261101/requests.json)。

预处理与搬卡1.012秒，模型生成7.913秒；本进程PyTorch峰值reserved显存14.56GiB。这些数值不含准备素材和前两次故障排查。首次两次均停留在CPU音频padding，未生成文本，日志分别保留于attempt1、attempt2。默认音频补齐长度为300秒；最终按整批最长音频向下取整后加2秒，本批补至12秒，完整保留所有原音频样点并使用GPU STFT。没有裁短音频来换速度。GPU7有其他任务，整体利用率100%不能作为本进程单独满载的证据。

脚本：[输入核验与生成](../scripts/p2_j_omni3b_plan24.py)、[审阅页面生成](../scripts/build_p2_j_plan24_review.py)。运行环境为共享的 `Omni-LTX-stage2/.venv`。已有结果受到覆盖检查保护；若改prompt做下一轮，应使用独立输出目录，保留本轮原始结果。

### 初步质量判断

**原始3B已经能输出一些合理候选，但这版prompt下的规划明显单一，尚不适合直接作为可靠的批量规划器。** 这一结论仅适用于本轮24条及本轮prompt，不能据此认定模型无法通过prompt改善，更不能认定LoRA必不可少。

下表来自逐条文本检查，并结合参考图和已有speaker转写；尚未逐条听审。音频已嵌入页面供复听，不能将这份检查当成盲评准确率。

| 观察 | 数量／例子 | 含义 |
| --- | --- | --- |
| 全部安排轻微点头 | 24／24含“nods slightly” | 行为选择过于集中；尚未证明能依据上下文规划丰富反应 |
| 计划停在“回应前思考” | 10／24含“before responding” | 没给出实际回应或明确沉默，指令执行不完整 |
| 声音计划明确程度 | 6条给出具体说话内容；2条明确无声；其余16条不够明确 | 包含含糊的non-verbal expression、未说明是否可听的呼气和未完成的回应意图 |
| 有语义适配能力 | #5瞬移愿望→“That sounds like a great idea.”；#22被责骂→“Yeah, that sounds really tough.” | 并非完全无视音频；但完整句是否抢话仍需AV验证 |
| 角色混淆 | #23把speaker关于车的长句复述为listener自述 | 明确违反“不复述speaker”和“简短回应” |
| 无依据的否定／情境补充 | #4对开放问题给出否定摇头；#17推断否定个人经历；#20把口述梳头写成listener正在观察该事件 | 需要减少多余推断，并保持听者角色 |

#14是相对完整的保守候选：“The listener nods slightly and maintains a neutral facial expression, indicating attentiveness to the speaker's words. There is no audible response from the listener.” #24的微笑配合动物故事也可以成立，但仍遗漏声音状态。

原listener标注和规划不一致不自动等于错误，例如原音轨静音时，另一种合理候选可以包含短促附和。原标注本身是弱标注，24条中11条历史标注框与最终裁框不同。本轮未根据标注一致率选优，也未对24条输出做修改。

### 下一步初步建议

先保留本轮作为冻结3B基线。可以再做一轮小范围prompt对照：明确要求给出可执行的脸／头动作、明确有声或沉默；若说话只能给短促反馈；禁止“准备回应／思考后回应”这种未完成计划，并再次明确不能代speaker复述。仍不强制JSON或精确时间，也不硬性规定必须点头。

这轮改进尚未执行。若仍有角色混淆、声音状态不明确或明显模板化，再推进描述生成LoRA的回答token交叉熵训练；之后比较预测描述驱动的实际音视频效果，决定是否需要生成侧适配。24条适合冒烟检查，不足以决定最终模型优劣。
