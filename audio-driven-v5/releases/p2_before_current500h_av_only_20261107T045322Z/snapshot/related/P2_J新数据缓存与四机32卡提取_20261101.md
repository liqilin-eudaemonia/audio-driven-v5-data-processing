## 实际训练输入

读取 J 原始 TAR 视频，按原样本时间区间以 25 fps 取最近 PTS，使用最终修正裁框，输出 512×512 RGB。训练不会读取复核网页中的有损 MP4。参考图为该视频的第一帧。

listener 音频严格执行原 caption 的官方 word/sentence/VAD 并集、100 ms 边缘和 10 ms 淡变配方；speaker 使用配对参与者同一绝对区间的归一化音轨。speaker 不经过 listener 的静音门控。原 caption 与实际音轨不一致时保留两者，例如 S1877 不因文字写了静音而再次静音。

全流程不生成新的中间 WAV/MP4。视频按原生 8n+1 约定补末帧；音频补齐、因果支持 mask、首帧 latent 替换和音频末端 token 裁剪沿用现有原生实现。

## Prompt

Qwen 使用显式 system 消息，完整任务说明在图像和音频之前：

```text
You model natural audiovisual responses for a listener in a conversation.

The reference image shows the listener. The input audio belongs to
the other participant, who holds the conversational floor. The
listener's response spans the same time interval as the input audio.

Use facial expressions, head movements, and brief vocal feedback
appropriate to the speaker's meaning and tone, while remaining in
the listening role.

Preserve the listener's identity. Align mouth movements with the
listener's own vocalizations. The output audio contains only the
listener's vocalizations and natural silent intervals.
```

user 消息仅放参考图与 speaker 音频。直接生成缓存到 assistant 起始前缀；指导版本在相同前缀后追加完整具体 P 与原生 `<|im_end|>`。P 为 Gemma 固定说明加 `Listener response description:` 以及原 caption 全文，不重写、不截断、不把整段描述捏造成带时间点的事件。Qwen 与 Gemma 使用同一份 P。

Gemma 直接编码文本，不采用 system/user 聊天结构。固定文本 G 为：

```text
A continuous close-up video of the person in the reference image
listening to another person speaking off-camera. The camera remains
fixed, and the person's identity and background remain consistent.
Facial expressions, head movements, and brief vocal feedback, when
appropriate, form a natural listening response. The person remains
in the listening role throughout. The soundtrack contains only the
listener's own vocalizations and natural silent intervals. Mouth
movements match the listener's own vocalizations.
```

直接分支的 Gemma 正向输入为 G；指导分支为 `G + "\n\nListener response description:\n" + caption全文`。负向文本均为空字符串。指导分支将这份完整 P 同时用于 Qwen assistant 和 Gemma，不仅仅把 caption 单独追加给 Qwen。原始自然语言 caption 不转成旧时间区间列表。

完整字符串及消息布局见 `src/p3_listen/prompts.py` 和运行 manifest 的 `prompts`。prompt 与代码指纹进入缓存身份，旧 system 缓存不能静默复用。

## 加速配置与实测

参考了既有[28 卡特征压测](P2_特征抽取28卡配置压测.md)、[全量提取巡检](P2_全量特征抽取接续与资源巡检.md)和[四机整体吞吐优化](P2_四机32卡整体吞吐优化_20261031.md)。

| 环节 | 生产配置 |
|---|---|
| 元数据冻结 | 64 个 CPU 进程，复用来源解析，断点保留已冻结样本 |
| Gemma | 每卡 1 个常驻进程，batch=32，完整 1024-token 原生路径；超长 P 使用原生扩展长度且拒绝截断 |
| Qwen＋VAE | 每卡 2 个常驻进程，每进程主要计算 2 线程 |
| 供数 | 每进程预取 8 条，由 8 个独立 CPU 进程解码；每机 128 个解码进程，有界队列 |
| Qwen 复用 | CPU 提前处理参考图与 speaker；两种条件复用同一个多模态前缀，仍分别运行语言模型 |
| 视频裁剪 | 保留 AVFrame 属性的 YUV ROI＋32 对齐上下文，再执行原 RGB/PIL 裁剪；原样本逐像素验证 |
| 写盘 | 每进程 2 个异步写入线程，原子落盘、SHA 校验和逐张量回读校验 |
| 任务调度 | 四机共享动态队列；文本任务每块 256 条，特征任务每块 32 条；flock 独占在途任务 |
| 显存 | `expandable_segments:True`，VAE workspace 不串行化 |

大批量压测沿用同一批 24 条原 caption，重复填满 batch，仅用于比较配置。batch=32 在未受其他任务影响的 23 张卡上平均 11.71 条/秒/卡，峰值 reserved 133.30 GiB。batch=64＋每 8 条分块投影在全部 32 卡通过，平均 9.87 条/秒/卡，峰值 96.91 GiB。两种大批量文本结果均与基准逐值一致。由于 32 更快，生产选择 32；该吞吐只代表 Gemma 常驻模型阶段，不等于整条缓存流水线吞吐。

node12 的 GPU5 一次被重新启动的外部任务占去约 19 GiB，造成 batch=32 OOM；已按用户授权强制结束，释放显存后的 batch=32 补验通过。生产启动器在本次运行期间清理占用这些 GPU 的其他计算进程，并记录 PID 与时间。node8 的实际内网地址为 `172.29.104.233`。

## 运行与读取

```bash
PY=/private/liqi_workspace/project_code/Omni-LTX-stage2/.venv/bin/python
WORK=experiments/p2_j_train500h_cache_20261101
$PY scripts/p2_j_cluster.py prepare --work "$WORK" --workers 64
# 各机分别执行；rank 为 0、1、2、3，node 为对应机器名。
$PY scripts/p2_j_cluster.py node --work "$WORK" --node node8 --rank 0 --prefetch 8 --media-processes 8
$PY scripts/p2_j_cluster.py status --work "$WORK"
```

每台机器使用全部 8 张卡，模型驻留跨任务复用；异常不会写成功回执，重新启动会跳过已完成任务。`workers/` 为进度和错误，`state/` 为完成回执，`telemetry/` 为每 2 秒 GPU 采样，`launchers/` 为节点启动状态。

训练端通过 `p2_j_cache.runtime.CacheReader(work).training_sample(sid, variant='direct'|'guided')` 读取既有 ConditionInputs、AV latent、支持 mask 与正负文本结构。该接口验证模型和数据身份；正式训练调度尚未启动。

`p2_j_cache_audit.py watch --work "$WORK" --processes 64` 每30秒检查进度、错误和心跳；全部任务完成后，自动逐条核对成功回执、四种缓存身份和实际输入来源，成功才写 `COMPLETE.json`。每份payload已在生成时完成SHA256及逐张量回读验证，最终遍历不重复编码模型。

按用户要求，四机提取继续在后台运行，监控与最终验收也已转为独立后台进程。监控进程信息保存在 `background_monitor.json`，输出写入 `logs/background-watch.log`；实时进度见 `status.json`。当前仍在提取，完成状态以 `COMPLETE.json` 为准。
