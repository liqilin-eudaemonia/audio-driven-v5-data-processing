# 修正版裁框流水线性能复查（2026-10-31）

结论：当前配置不能称为最优。运行正确性与资源利用率是两件事；主要可优化区域在 CPU 输入准备、修正点头与视频解码的重复工作，以及来源任务之间的预取衔接。此次没有修改裁框规则、音频配方、帧率、prompt、token 上限或 GPU 模型参数。

## 实际观察

生产目录 `experiments/listen_j_omni_20261030/`。四机 32 卡持续运行，采样通过固定状态文件和 GPU 查询完成，没有扫描结果目录。

40 秒基线窗口合计 3.974 段/秒，平均 GPU 利用率 10.51%。这是短时间吞吐，不能代表全量平均速度或直接用于完成时间预测。

| 节点 | 段/秒 | 平均 GPU 利用率 | CPU 使用核数／配额 |
|---|---:|---:|---:|
| node17 | 0.425 | 6.74% | 133.2／160 |
| node8 | 1.250 | 11.58% | 116.9／160 |
| node4 | 1.225 | 12.08% | 111.7／160 |
| node12 | 1.074 | 11.64% | 131.6／160 |

四机修正版点头重算槽位均观察到 16/16 占用；总解码槽位仅占用 39–59/112。部分生产样本准备耗时约 29–58 秒，生成调用约 1–6 秒，但生成调用可能含多条输入，不能直接当作单条纯 GPU 时间。准备等待指标还与 GPU 工作重叠，不能当作互斥的 GPU 空闲时间。

当前主程序每卡使用一个模型执行序列，最多提交 4 个已准备请求；这不等于真正的 GPU batch=4。node17/node4 每卡 8 个准备进程、预取 16；node8/node12 每卡 4 个准备进程、预取 8。

## 有限配置试验

临时将修正点头槽位由每机 16 提至 24，无需重启 GPU。40 秒过渡窗口为 4.749 段/秒，随后 60 秒窗口为 4.398 段/秒；后者平均 GPU 利用率 9.81%。node8 改善较明显，node4/node12 未同步改善。

这些窗口处理不同片段，受时长、分辨率、是否变框及来源任务尾部影响，不能据此声称全流水线获得固定加速比例。因此恢复为每机 16，回切后的 60 秒窗口为 4.316 段/秒、平均 GPU 利用率 9.90%，与 24 并发后续窗口接近。该回切窗口可能含正在排空的旧并发请求，也不能作为严格因果对照。没有将 24 统一固化为推荐配置。

## 像素一致的裁剪试验

在独立 CPU 进程中，对 4 个实际修正版输入比较：

1. 生产路径：`crop_resize(frame.to_image(), transform)`。
2. 已有优化函数：`frame_crop.crop_original_frame`，避免先构造整张高分辨率 PIL 图像。
3. 已有复用转换器函数：`crop_original_frame_reused`。

保持采样、RGB 转换、bicubic 缩放、JPEG85 和时间检查不变。4 段模型输入的帧字节 SHA256 与视频元数据 SHA256 全部一致。

- 生产路径累计：44.665 秒。
- 减少 PIL 整帧复制：35.928 秒，累计耗时减少 19.6%。
- 复用转换器：38.907 秒，收益较不稳定。

采用交替执行顺序，但生产负载仍在变化，这只是小样本组件测试。19.6% 不是全流水线提速比例。此次仅在隔离测试函数中替换调用，尚未改动生产 `full_raw.prepare`。

## 后续优化优先级

1. 接入并验收已有的像素一致裁剪函数，先验证完整输入指纹，再做单卡完整生成对照。
2. 对变框片段减少重复解码。目前修正点头先解码／裁剪一次，Omni 又独立解码同片段。复用需保留原 PTS、8 fps 与 25 fps 各自采样、JPEG85，以及临时缓存的释放与来源校验，不能简单用重编码后的视频替代原输入。
3. 让待处理来源之间也能连续预取，减少单个来源末尾只剩少量慢输入时的 GPU 等待。
4. 上游点头尾部接近完成时重新分配 CPU，并按节点测并发，避免统一增加 CPU 争抢。不能把旧 Qwen3-VL 的大 batch 配置直接视为当前 Omni 的已验证配置。
