# 规划 SFT 后的 500h hidden states 接续提取

本轮按用户确认的顺序执行：当前独立 Feature teacher 提取和全量验收完成 → GPU 小样本验收 → 四机 32 卡重新提取 guided H。运行入口为 [运行目录 README](../experiments/p2_j_train500h_sft_hidden_20261102/README.md)。状态以该目录 `chain_status.json`、`CANARY.json` 和 `COMPLETE.json` 为准；排队不等于已经完成 GPU 验证。

## 数据、模型和变化范围

- 数据仍是当前 500h 的 **285,638 条 train**，完整成员来自 `experiments/p2_j_train500h_cache_20261101/manifest.json`，不扩展到规划 SFT 的 1,155h，也不加入 dev/test。
- 基座 `/public/2_CKPT/3_PreTRAINED/Qwen2.5-Omni-3B`。
- 加载已完成 2,697 步的 `experiments/p2_planning_sft_filtered_3b_24gpu_inputfast_isolated_20261102/final_adapter/`。这是语言模块规划 LoRA；冻结后以未合并的 PEFT 形式提取，权重 SHA256 写入独立缓存身份。
- 只新提取 `input_plan`：第 8／18／28／35 层 H，每层 2048 维。保留原始多模态前缀、完整标注指导文本及原生 `im_end`，不截断。
- 输入为最终修正版 listener 裁框首帧、配对 speaker 音频和原打标描述。文本仍采用原 AV guided 缓存的完整 prompt；不会先让新 Qwen 重新生成描述再替换原文。
- listener 净化音频不作为 Qwen 输入；它在已有 AV latent 和独立 teacher 中作为真实目标。已确认的静音配方和音画时间不变。
- 原 H、Gemma 文本缓存、AV latent、独立冻结 teacher 都保留；本轮不重新计算后三者。没有启动 LTX 或联合训练。

## 沿用的提取代码和优化

直接调用原生 `src/p2_plan_cache/encoding.py::extract_planned_input` 与 `src/p3_listen/features.py::prepare_prefix/prefix`，没有重写 H 的数学定义。原生 frozen Thinker 上注入 LoRA 后，使用 `PeftModel.get_base_model()` 获取正确的 Thinker 入口，避免把 PEFT 外层 `.model` 错当成文本 transformer。

参考 [四机提取交接](P2_J新数据缓存与四机32卡提取_20261101.md)，采用：

| 项目 | 本轮配置 |
|---|---|
| 节点 | node8、node17、node12、node4，各 8 卡 |
| 常驻模型 | 每卡 2 个进程，共 64 个 |
| CPU 供数 | 每模型进程 8 个独立 producer、预取 8 条；完成顺序消费 |
| 首帧 | 复用经原图像素 SHA、最终裁框及来源审计核验的 512×512 PNG |
| 计算 | 原生逐片段 H 提取；不套用 Gemma 的 batch32，也不改变注意力或 padding 语义 |
| 写盘 | 每进程 2 个异步线程；原子写、SHA256、逐张量回读一致性 |
| 调度 | 共享动态队列，每块 128 条、flock 独占；完成 worker 可以领取其他块 |
| CPU/显存 | 主进程 Torch 2 线程，producer 1 线程，expandable_segments |

本轮不需要解码完整 listener 视频。复用可验证的首帧，可以减少重复解码及文件读取；拒绝损坏或来源不一致的参考图。整体吞吐需由本轮实际记录确认，不能把先前 Gemma 批量速度当作 H 提取速度。

## 接续与验收

新增代码仅位于 `src/p2_j_sft_hidden.py`、`scripts/p2_j_sft_hidden.py`。正在运行的 teacher 代码、原缓存源代码及其身份均未改动。

1. CPU：32 条核对最终首帧、配对 speaker、原文 token 和前缀长度；其中 8 条从原始视频重新取首帧，核对全部 processor 张量逐值一致。结果 `CPU_CHECK.json`。
2. 等待 teacher 的 `production/COMPLETE.json`：必须全量 285,638 条、源路径和 protocol SHA 一致。仅计数完成不足以开跑。
3. 确认四机 32 卡已释放，连续两次资源检查通过；不终止其他任务。
4. GPU canary：32 条加载最终 SFT LoRA提取 H，检查来源、token、几何和训练包拼装；前 8 条与未优化的原生提取逐值对照，关闭 LoRA 时必须复现旧 H；开启后 H 必须实际改变。通过才写 `CANARY.json`。
5. 启动四机全量提取。新旧权重具有不同缓存身份和目录，不能静默混用。节点子进程故障允许有限重启，只清理自身子进程组；失败块单独记录，不冒充完成。
6. 全量核对成员、源身份、payload 回执及大小后写新 `COMPLETE.json`。CPU 测试、GPU canary 和全量完成是三个不同状态。

`chain_status.json` 会标记 `waiting_teacher_audit`、`waiting_resource_release`、`gpu_canary`、`extracting`、`auditing`、`complete` 或 `attention_required`。状态写盘不会重新开启此前已停止的 20 分钟聊天汇报。
