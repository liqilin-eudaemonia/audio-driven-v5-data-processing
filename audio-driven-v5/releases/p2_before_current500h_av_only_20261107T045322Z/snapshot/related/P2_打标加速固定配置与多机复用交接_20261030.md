## 1. 当前结论与证据

node17（172.29.15.91）8 张 H200，每卡一个独立 Qwen3-VL-8B 实例。推荐复用 **batch512／调度 token budget32768＋CPU 进程解码＋输入预处理重叠＋连续补入请求**。

| 对照 | 结果 | 可得结论 |
|---|---|---|
| 同样本、每配置两轮：batch256/token16384 → batch512/token32768 | 0.41411 → 0.44392 段/秒/卡 | 约提升 7.2%，不是全局最优证明 |
| 最近完成的稳定生产窗口，600.575 秒 | 视觉新增 3050 段，5.078 段/秒；点头新增 2699 段，4.494 段/秒 | 当前真实运行量级；不同来源不可作为严格 A/B |
| 同一生产窗口资源 | GPU 平均约 64.0%，CPU 约 142/160 核 | 输入准备仍占时间；显存占用或 GPU 瞬时峰值不等于吞吐 |

视觉和点头是同一批片段的两条分支，**不能把两者速度相加当成完整片段吞吐**。当前输入含 4K、1080p 和不同时长，后续 ETA 应使用近期完成增量。处理完成、结构有效、语义准确分别统计。

## 2. 固定的输入与输出规格

- 模型 `/private/ckpts/Qwen3-VL-8B-Instruct`，观察式 C prompt，原生视频 8 fps。
- 按 listener 的原始 `crop_proposals.listener` 裁框，整数 half-up 取整，缩放到 512×512，JPEG quality85；缺框/无效框不能用原画替代。
- 保留整段请求及 3 秒窗口、1 秒步长，不能为加速删窗口、减帧、缩短片段。
- temperature=0，seed=20261029，每请求输出上限4096，模型上下文上限49152。**32768 是调度 token budget，不是输出长度。**
- 视觉分支不输入音频；listener 音频引用保留，本轮不代表新跑了 ASR。
- GLARE recall 点头使用同片段、同裁框的25fps姿态；专用摇头关闭。
- 只导入 J 的已提交 `result.json`，用 `complete.json` 与来源 SHA 核验；不使用 `initial.json` 替代最终切分。
- 原文、时间、来源、无效响应及失败原因保留；`training_admitted=false`。不覆盖原始数据，不新增 WAV。

完整标注语义见[原生视频8fps与点头补充交接](P2_原生视频8fps与点头补充打标交接.md)。

## 3. 推荐复用参数与实际运行差异

| 参数 | 推荐复用基线 | 范围 |
|---|---:|---|
| batch_size | 512 | 每 GPU 未完成请求预算 |
| tokens | 32768 | 每 GPU 调度预算 |
| frames | 16384 | 每 GPU 连续调度帧预算 |
| clip_batch_size | 50 | 每组最多50段，跨来源凑组 |
| memory | 0.80 | 每 GPU vLLM 显存比例 |
| prefetch | 1 | 一个 CPU 预取组 |
| rolling_annotation_groups | 2 | 连续补入的标注组容量 |
| decode_backend | process | spawn CPU 子进程，清空 CUDA 可见设备 |
| decode_workers | 16 | 每 GPU 解码池容量 |
| decode_slots | 112 | **整台机器共享**的解码并发槽，不是每卡112 |
| renderer_workers | 2 | 每 GPU 输入 renderer |
| nod_workers | 80 | **整台机器**点头 worker 数 |
| eager | false | 使用 decode-only CUDA Graph |
| graph capture sizes | 1,2,4,8,16,32,64,128 | compilation mode0、FULL_DECODE_ONLY |
| prefix_caching / mm_processor_cache_gb | true / 0 | 保留 prefix cache，关闭该多模态处理缓存 |
| precompile_inputs / shared_frame_arrays | true / true | 输入预处理与帧数组共享 |
| rgb_reuse_gpus | [] | RGB 复用试验已撤回 |

**当前 GPU7 是例外**：仍运行4个标注组、graph最大256；没有证明比2组/128更快。为避免无收益重启，原进程保留，但新部署不默认推广这个例外。GPU0～6使用推荐基线。

有效参数由 `selected.json`、`config.json.gpu_execution_overrides`、`resource_tuning.json` 共同决定，以 worker 心跳中的 `execution` 和动态 `*_active` 字段核验。`selected.json` 中 memory0.85/eager=true 属于早期测速记录，**不能只复制这个文件就声称复现当前配置**。`config.json` 的早期 decode_workers4/slots32 也已被运行时调优覆盖。

[参数与原始配置快照](../experiments/listen_j_annotation_node17_20261029/frozen_config_20261030/recommended_reference.json)包含推荐基线；同目录保存实际逐卡配置、原始三份配置及 SHA256。该 JSON 是交接参考，不是可直接传入集群入口的运行配置。

## 4. 提速来自哪些改动

1. **跨片段批量请求、按预算连续补入**：已完成请求释放预算后补新请求，避免整组所有长响应结束后才接下一组。引擎由主线程调用，用请求ID回传，输出仍按来源组顺序提交。
2. **严格限制每组50段**：一个含数百段的来源拆成多组，避免准备大来源时 GPU 长等。来源锁跨组保留，只有全部片段完成才写来源完成凭证。
3. **CPU 进程解码**：用独立子进程隔离 Python 执行与解码；GPU 进程专注推理。16路是池容量，112共享槽限制整机争抢。
4. **预取、预编译、2路 renderer**：提前构造官方模型输入，解码、输入准备与 GPU 推理重叠，窗口尽量引用同一份帧数组。超内存预算回退原路径，不裁掉数据。
5. **等价裁剪与可信临时缓存**：保持原像素/时间/元数据协议，减少重复转换和搬运。临时输入缓存只在可追溯条件下复用，持久输出完成后清理。
6. **decode-only CUDA Graph**：减少生成阶段调度开销，保留既定输入与采样参数。
7. **两分支持久队列和故障恢复**：视觉/点头分别计数，断点跳过已有输出；用 PID＋启动标识检查存活，防止旧心跳或复用PID误判。

这借鉴了“跨卡工作量均衡、提前准备不变输入”的思路，**没有预计算 T5**：当前是 Qwen3-VL 打标链路，预计算的是帧与模型输入准备。

## 5. 未推广的试验

- 128个共享解码槽：未见可靠增益，恢复112。
- GPU7四组调度和256图捕获：只有单卡试验，来源混杂，无可靠因果提速结论。
- NVDEC/hybrid：部分8bit素材单流快，但8路并发反而慢，High10素材还受硬解支持限制；生产仍为 CPU process。
- RGB formatter复用：16段/713帧同输入基准像素一致，CPU准备均值25.59→20.35秒；尚未完成生产吞吐验证，已撤回单卡试验。
- YUV局部裁剪：10bit输入像素不一致，不采用。

以上代码可能仍在仓库中；代码存在不表示生产启用。停止优化探索后只处理故障，不自动启动新试验。

## 7. 推广到多机多卡的方法与当前限制

**可复用的是每卡执行策略；当前启动器尚不是通用多机调度器。** supervisor默认有node17主机名保护，现可通过expected_hostname明确指定目标主机，execution profile限制卡号0～7，队列和守护使用单机PID身份及工作目录锁。不能在另一台机器直接复用 node17 的工作目录，也不能声称已有24卡集群验收。

后续部署按以下步骤实施：

1. 每节点独立工作目录、日志、临时缓存、锁、监督和队列；每台本地GPU编号0～7，分别启动模型副本，不把独立推理强改成跨机张量并行。
2. 先固定来源分片清单，按预计解码/窗口工作量均衡分配；整条来源只归属一台节点，来源内仍按50段拆组。记录分片映射与SHA，恢复时沿用。新入口需支持分片导入，不能让现有 ingest 在每台各导入全量。
3. 显式适配并验证主机配置和启动器保护；**不要复制 supervisor.json、watchdog.json 或 inflight/PID 状态到新节点**。来源和已有结果保持只读，可据完成凭证排除已完成部分。
4. 对同规格8卡节点使用上述基线作为起点；16路/卡、112共享槽、80点头是整机资源配置，不能按总卡数乘到每台。CPU、RAM、共享存储较弱时降低并发；不得为了显存数字好看挤占输入资源。
5. 每节点先做小批部署验收：同帧像素/时间/裁框、prompt与窗口不变；来源唯一、全部窗口及无效响应有记录；CPU子进程无CUDA；续跑不丢不重。随后稳定运行10分钟，核对真实完成增量、失败队列、无OOM和进程身份，再接满分片。这是部署验收，不再做宽泛参数搜索。
6. 汇总以 sample_id 与来源SHA去重，独立统计视觉、点头及两分支交集完成数；验收分片并集等于目标全集、分片互斥、失败有清单。不能只累加来源数或把生成了JSON当作有效标签。

若未来需要跨节点动态抢任务，应先实现带节点身份的租约和故障回收；现有单机PID协议不能直接充当分布式租约。
