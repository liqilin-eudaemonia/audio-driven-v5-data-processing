# J 切分打标：修正版裁框接续与旧标签保留（2026-10-31）

## 已确认的处理边界

用户确认：后续使用 `quality-bounded-crop-v1-20261030`；已经完成的标签保留，即使修正版裁框改变，也不重新生成，并注明旧框来源。不得把旧框标签宣称为修正版输入结果。

本次修正的是打标输入裁框。原始 J 切分记录、样本 ID、人物身份、源视频起止时间、官方 listener 词／句／VAD 并集净化配方、音频样本数均不改变。没有重新 ASR，没有导出新 WAV。

## 修正版从哪里来

使用现有画质测量记录 `crop.new`，复用 `src/listen_benchmark/j_quality_pipeline.py::cropped_row`，不另行推算裁框。

- 只处理画质 `retain` 的片段；`exclude`／`review` 不送入 Omni。
- 校验质量策略、原始 source 指纹、测量文件 SHA256，再应用整数方框。
- 修正框须位于原图内，保持方形，边长最多为旧框的 1.05 倍。
- 修正版为已确认的有界平移／小幅扩大策略；其头顶范围来自估计，并不等于逐帧发型或完整头部人工验收。
- 测量阶段旧契约的 `apply_crop_proposals=false` 保留：该阶段负责测量；新增 `config.json.bounded_crop_input` 明确负责在后续输入阶段应用修正版。不会篡改历史测量契约。

## 点头与 Omni 如何保持一致

1. 完成的 caption 文件保持逐字节不变。
2. 对待处理片段取得修正版坐标。
3. 坐标不变：复用已有 25 fps 点头结果。
4. 坐标改变：优先读取上游已按修正版计算的点头；否则在单独的 `corrected_crop_v1/nod/results/` 缓存中重新计算。不能直接把旧框点头结果当成新框检测。
5. Omni 以完全相同的修正版裁框生成 512×512、8 fps 视频输入，并使用相同时间原点的净化 listener 音轨。
6. 新输入的生成尝试放在 `attempts_corrected_crop_v1/`，不读取旧框未完成的重试文本。

修正点头运行于常驻 CPU 子进程，复用导入环境并逐段创建检测器，当前每机额外最多 16 个任务；沿用已有解码限流。它只在通过画质且需要后续 caption 的片段上执行。

## 结果读取与来源字段

生产目录：`experiments/listen_j_omni_20261030/`。

- 已完成旧标签仍在 `caption/results/<hash>/<sample_id>.json`，原有 `source.video_transform.crop` 和 `source.crop_proposal.revision` 就是当时实际裁框。没有 `crop_provenance` 的历史结果按旧版处理，不能默认是修正版。
- 新结果的 `source` 是实际输入的修正版来源；`original_source` 是未经修改的 J 来源。
- `crop_provenance` 同时记录原框、实际框、是否变框、修正版名称、质量测量路径和 SHA256。
- `input_evidence.crop_application` 是进入模型前记录的同一份裁框证据；`input_evidence.nod_supplement.detector_file` 指向真正使用的点头结果。
- 读取入口 `src/listen_benchmark/j_omni_crop.py::caption_crop_info(result)` 可以统一识别新／旧来源。旧结果返回 `label_origin=legacy_original_crop_preserved`；新结果返回 `corrected_crop_pipeline`。
- 恢复执行时按 `original_source` 对照原始任务，另外核对新结果的实际 `source` 与修正版一致。旧标签直接跳过，不覆盖。

滚动切换期间，旧进程已经准备／正在生成的输入也按实际旧框记录；以进程验收完成为全体切换边界，不能用配置启用时间反推所有标签的版本。

整份结果允许包含旧框已完成标签和新框后续标签，这是用户明确选择的保留策略，不表示所有标签都已基于修正版重新生成。下游采用新视频裁框时，旧标签仍必须携带上述来源区别。

## 部署时的接续修复

初次给上游点头启用修正版时，只查找下游画质回执，导致尚未入 Omni 队列的来源缺少回执文件。在计算点头之前即报错，没有写出错误点头标签。已改为直接验证上游持有的前置 decision，并用真实未发布来源验证。

219 个因此进入失败队列的来源任务已保留失败记录、清理该次重试计数并放回待处理队列，不改变源数据和已有输出。恢复记录在 `corrected_crop_rollout_20261031/early_queue_recovery.json`；该数是来源任务数，不是片段数，也不表示恢复任务已全部重新处理完成。`early_replay.json` 和对应测试覆盖“上游回执已有、下游回执尚无”的顺序。

GPU 部署验收确认四机 32 个进程均使用修正版并已有新输出，核验 8 份新输出的实际来源与点头裁框，以及 8 份旧标签的文件哈希。相关测试共 65 项通过。CPU 接续状态另见 `corrected_crop_rollout_20261031/upstream_audit.json`。
