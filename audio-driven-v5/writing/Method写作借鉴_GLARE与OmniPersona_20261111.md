# Method 写作借鉴：GLARE 与 OmniPersona

记录日期：2026-11-11。

本文汇总本轮对两篇参考论文 Method 段落的讨论，供继续撰写本项目的方法部分时查阅。重点是章节组织、段落逻辑、公式与信息流的衔接，以及如何把写法应用到自己的实现。本文记录写作建议，不代表新增模型设计、修改训练配置或完成效果验证。

参考材料为作者在会话中提供的原文，以及本地 [GLARE](00_GLARE_local.pdf) 和 [OmniPersona](OmniPerson.pdf)：GLARE §4.1–4.4；OmniPersona §3.1–3.5。当前项目的两项损失实现另见 [Feature与Event监督详解及结构图画法](Feature与Event监督详解及结构图画法_20261110.md)；正文后移的细节见 [补充材料待补内容清单](补充材料待补内容清单.md)。返回 [写作总索引](README.md)。

## 1. 阅读与使用顺序

- 用两篇论文的 Overview 学习“任务—条件—生成—输出”的总体叙述。
- 用 GLARE 的模块段落学习“困难—设计—监督”的局部论证。
- 用 OmniPersona 学习模块接口、基座与本文设计的区分，以及复杂框架的组织。
- 将这些写法映射到本项目的条件构建、Feature 和整段 Event。
- 最后检查正文与实现细节的分工，以及方法主张是否有对应证据。

**核心原则：每个模块都要说明职责、输入输出、计算过程及设计理由；每一步的输出都应当能够接到后续生成或监督过程。**

## 2. Overview：先让读者理解整个系统

### 2.1 OmniPersona 可以借鉴的地方

其 §3.1 按下面的顺序展开：

```text
任务目标
  → 定义对话上下文与人物参考
  → 写出条件生成关系
  → 指向架构图
  → MLLM 产生内容与上下文表征
  → Connector 构造生成条件
  → 条件进入视听生成器
  → 生成结果进入后续对话
  → 说明具体基座与后续小节分工
```

值得借鉴的写法：

1. **先解释模块承担什么职责，再落实到模型名称。** 读者先知道理解、条件构建、生成之间的关系，再理解 Qwen 和 OVI 的位置。
2. **沿着信息流介绍模块。** 上一个模块产生的内容，紧接着成为下一个模块的输入，不在无关的实现细节之间跳转。
3. **让任务和架构相互对应。** 其任务要求多轮对话和身份一致，因此 Overview 交代历史记忆、参考信息与输出回写。
4. **公式服务于必要定义。** 对话上下文、人物参考和生成目标各有作用；不应仅为了模仿形式而增加同样数量的公式。

对本项目的应用：我们应解释当前 speaker audio、listener reference image、反应描述、条件表征和视听输出之间的关系。历史记忆、参考声音和跨轮回写属于参考论文的任务设计，不自动成为我们的模块。

### 2.2 GLARE 可以借鉴的地方

其 §4.1 先说明参考图像和 speaker audio，随后逐项说明参考运动、身份、声学及情绪表征的来源与含义，再把条件连接到生成过程：

```text
输入与特征编码
  → 构造 driving condition
  → 条件作用于带噪 motion latents
  → Transformer 预测 vector field
  → 求解得到 motion latents
  → 结合身份表征并解码视频
```

这一段最值得借鉴的是**生成过程交代完整**：既说明生成器使用什么条件，也说明预测什么、如何得到最终媒体。

对本项目，应明确：LTX 对带噪视频和音频 latents 预测 flow velocities；采样器迭代更新 latents，最后再解码为 listener 视频和音频。不能把“最后一个 block 的 hidden”“预测速度”“最终 latent”和“解码后的媒体”混为一谈。

### 2.3 本项目 Overview 的内容顺序

当前会话中的 Overview 已具备任务、条件构建及监督位置，推荐按四个内容块组织：

| 内容块 | 需要回答的问题 | 保留的核心内容 |
|---|---|---|
| 任务定义 | 输入什么、输出什么、处于哪个交流阶段？ | 输入输出公式；对方持有话轮期间的视觉与声音反馈，含安静倾听 |
| 整体架构与条件形成 | 如何从当前话语得到生成条件？ | 架构图入口；Qwen 规划描述与 guided hidden；Connector、Gemma 及两路条件 |
| 联合生成 | 条件如何参与媒体生成？ | 原生 text cross-attention、speaker Whisper 分支、带噪 AV latents、速度预测、采样与解码 |
| 训练监督 | 训练时如何获得描述和约束模型？ | 标注描述替换预测描述；Feature 监督条件，Event 监督生成表征 |

**标题与重复处理：**

- 小节使用 `\subsection{Overview}` 时，不再重复设置 `\paragraph{Overview.}`。
- 任务定义可以作为本小节开头的自然段，当前建议不再单独加 `Task definition` 段标题。
- 前文已经介绍 Qwen 预测描述及条件构建时，不在结尾再次完整复述同一推理过程。
- 任务定义使用 `\input{draft_sections/03_task}` 或直接展开正文中的一种，避免正文和 `sec:task` 标签重复。
- 输入输出公式与条件拼接公式均可以保留。更细的 shape、池化规则及损失公式放到对应模块小节。

可借鉴的总览开场句：

> As shown in \cref{fig:method}, our framework combines reaction planning with joint audiovisual generation.

可借鉴的生成过程收束句：

> LTX jointly predicts flow velocities for noisy video and audio latents. Iterative sampling produces the final latents, which are decoded into listener video and audio.

这些句子是写作示例；具体描述与正式模型版本保持一致。

## 3. GLARE：如何把单个方法模块讲清楚

### 3.1 Prosody Conditioning：动机紧贴当前模块

它从当前模块要处理的困难切入：倾听反应可能与重音、情绪波动及韵律变化有关，条件需要反映这些线索。接下来立即提出韵律分支，再解释音频分析结果怎样变成生成条件。

其段落顺序为：

```text
指出需要补充的语音线索
  → 提出 prosody conditioning branch
  → 音频模型提取时间线索
  → 形成逐帧强度信号
  → 映射为紧凑特征
  → 与其他条件拼接、投影
  → 交给生成器
```

可以学习三点：

- 开头只说明这个模块的必要性，不重复整篇论文的对话背景。
- 介绍一个表示时，同时交代它来自哪里、表示什么。
- 最后明确该表示如何进入主生成路径，不能只说“提取了一种特征”。

用于我们的 speaker audio 分支时，应写清“为描述引导的条件补充直接声学信息—Whisper 特征—适配器—两路 cross-attention”。这一路径不同于 GLARE 的韵律时间线构造，不能把其提取机制写成我们的实现。

### 3.2 Temporal Reaction Loss：先定义预测与标签，再写公式

它先指出：视觉上合理的动作仍可能缺少与会话相关的反应。随后提出时间反应监督，再依次说明当前帧 hidden、中间表示、类别子空间、逐帧预测和标注目标，最后给出 Smooth-L1 损失。

其写作顺序为：

```text
连续重建目标的行为约束不足
  → 引入显式反应监督
  → 定义 hidden 与类别
  → 描述预测头和输出
  → 定义参考标签
  → 写出损失公式
  → 解释监督希望保留什么信息
```

公式出现前，读者已经知道预测量、标签、类别和时间维度的含义。因此公式承担“形式化已经解释清楚的过程”的作用。

对本项目，同样先说明 Event 预测的对象是**整段类别存在性**，再解释 pooling、分类头、标签与 BCE。GLARE 的逐帧目标、类别子空间和 Smooth-L1 属于其具体实现，不应直接替换我们的整段多标签设计。

### 3.3 Training Objective and Inference：紧凑地串起完整方法

GLARE 先给总损失，说明各项来源与作用，再用短段落交代推理输入、速度预测、ODE 求解和视频解码。

可以借鉴：总目标集中写一次；推理按实际执行顺序叙述；已经在前面定义的模块和符号直接复用。保留理解训练和采样所需的信息，具体超参数另放实现细节。

## 4. OmniPersona：如何组织完整生成框架

### 4.1 Connector 围绕模块接口组织

其 §3.2 先定义 Connector 的职责：把上下文理解结果转化为补充文本条件的非语言记忆。随后写清：

```text
上下文 C + 可学习查询 Q
  → Qwen 输出上下文化查询
  → 选取查询输出
  → 投影到生成条件维度
  → Transformer 细化
  → 与 T5 文本表征拼接
  → 生成器 cross-attention
```

可借鉴的具体写法：

- 一次公式对应一次重要变换，不让一个公式承担未解释的多种操作。
- 明确投影改变什么维度、拼接发生在哪个维度。
- 说明输出的下游用途，使 Connector 小节与生成小节自然衔接。

应用到我们的路径：

```text
反应描述引导的 Qwen 多层 hidden
  → Connector 的层表征整理与坐标查询融合
  → 两路条件 U_v、U_a
  → 分别与 Gemma 条件按 token 维拼接
  → LTX 原生 text cross-attention
```

我们在 Qwen 输出之后通过 Connector 读取多层 hidden；OmniPersona 则把可学习查询与上下文一起送入 Qwen。写作中应保持这个实现区别，也不能把我们的条件自动命名为“历史非语言记忆”。

### 4.2 联合生成先交代基座，再明确本文修改

其 §3.3 先介绍 OVI 的双分支及原生 attention／FFN，再说明各类 latent 如何参与计算，随后指出自己的核心改动：参考音频在跨模态融合中的参与范围。

对应的写作原则是：**基础架构提供什么能力，本文改变什么计算路径，两者分别说清楚。**

本项目可以这样区分：

| 层次 | 应如何表述 |
|---|---|
| LTX 基座 | 提供双流联合生成及原生跨模态交互，引用原始来源 |
| 条件构建 | 将 Qwen 的反应规划与表征映射为 LTX 可使用的条件 |
| Speaker 声学分支 | 补充直接声学信息，说明其注入位置与方式 |
| Feature 与 Event | 分别约束条件适配与生成表征中的反馈类别 |

用户已明确：speaker audio cross-attention 不单独作为主要 contribution。它仍需在 Method 中清楚解释，但不因独立介绍实现就自动成为一项主要创新。Feature 和 Event 可以在贡献表述中合为训练目标的改进，在方法正文中分别解释。

### 4.3 抗漂移段落展示“操作为何服务于目标”

其 §3.4 的重点不只是列出 Diffusion Forcing 或 Strided RoPE，而是说明：困难从何而来、操作改变了什么依赖关系、希望获得什么行为。

例如，参考图像位置偏移的解释形成了这样的链条：

```text
参考图像与连续视频存在位置关系差异
  → 调整位置编码
  → 将其作为全局身份参照
  → 服务于跨轮身份稳定性
```

可以学习这种论证方法。本文当前任务没有采用其多轮 prefix 抗漂移机制，不能因为借鉴写法而增加对应能力主张。

我们的设计也应说明“操作—目的”的关系：

| 操作 | 紧接着解释的目的 |
|---|---|
| 辅助特征解码器使用送给 LTX 的同一份 `U_v/U_a` | 让辅助任务约束真正用于生成的条件 |
| 从真实 listener 视频和音频提取冻结目标特征 | 提供与目标生成内容有关的学习依据 |
| Event 读取最后一个 LTX block 的 hidden | 将类别监督作用于生成表征，并沿生成计算图传播梯度 |
| 视频、音频分别做整段池化 | 分模态表达类别存在性，允许合理的事件时序变化 |
| 屏蔽未知或冲突标签 | 避免将缺少可靠证据的项强行作为监督目标 |

这些关系比仅罗列 MLP、pooling、BCE 等名称更能解释方法设计。

### 4.4 训练段落明确参数归属

其 §3.5 先说明哪些模块全参数训练、哪些基座参数通过 LoRA 适配，再定义训练目标与条件变量。

本项目也应区分：Qwen 反应规划器的微调、生成器训练时的参数更新范围，以及各损失的梯度路径。写作时依据最终版本核对，不能把两个阶段合写成所有模块都由同一个总损失联合更新。

关于 LoRA 的原生层范围、学习率、batch、采样步数等，以实际配置为准；借鉴的是清楚交代参数归属的写法，不是沿用参考论文的数值或更新范围。

## 5. 应用到本项目：各模块怎样写

### 5.1 每个模块先回答四个问题

1. 这个模块承担什么职责、处理什么困难？
2. 输入经过哪些变换，得到什么输出？
3. 输出如何进入生成器或损失计算？
4. 这些操作为什么能够服务于预期目标？

对应的段落角色可以是：**动机 → 表示与数据流 → 目标／公式 → 作用机制**。不必机械拆成四段；短模块可以在一个段落中完成，但不要混入不相关的工程说明。

### 5.2 Feature 与 Event 使用不同的动机

| 模块 | 动机 | 前向／监督叙述顺序 | 设计目的 |
|---|---|---|---|
| Speaker audio conditioning | 为描述引导的条件补充直接、连续的声学信息 | speaker audio → Whisper → adapter → 两路 cross-attention | 利用当前话语的声学线索 |
| Feature supervision | 理解模型衍生的条件需要适配目标视听生成 | 真实 listener 音视频 → 冻结特征 → 加噪 → 结合 `U` 预测特征速度 → 与目标速度比较 | 让条件保留与目标生成内容有关的信息 |
| Clip-level Event supervision | 连续媒体目标没有显式规定哪些反馈类别出现，合理回应时序又可变化 | 最后 LTX hidden → 分模态 masked pooling → event heads → logits → 标签、mask 与 BCE | 显式监督整段类别存在性 |

Feature 关注条件的适配；Event 关注反馈行为的表达。不要把二者都笼统介绍为“提高生成质量的辅助 loss”，否则读者难以理解为什么同时需要它们。

### 5.3 整段 Event 的理由放在公式之前

推荐论证顺序：

```text
连续视听目标没有显式标明反馈类别
  → 同一话语可以对应不同的合理回应时序
  → 采用整段类别存在性监督
  → 解释池化、预测头、标签与 BCE
```

可以使用的动机句：

> The audiovisual generation objective does not explicitly specify which feedback categories should occur. Since a reasonable reaction can occur at different moments within an utterance, we supervise category presence over the clip rather than exact event timing.

当前话语可以约束回应的态度或情绪方向，但不唯一决定具体动作类别和时刻。整段监督为反应时序保留变化空间；类别出现本身不能证明所有回应都语境适当。相关效果由独立生成评价支持。

### 5.4 Feature 公式前先解释预测对象

需要先交代：目标特征 `F` 来自真实 listener 音视频；带噪特征是辅助解码器的输入；监督对象是特征空间的 flow velocity；同一个条件 `U` 同时进入辅助解码器与 LTX。

随后再给加噪关系与速度损失。这样读者能理解为什么 Feature loss 更新 Connector，以及它与主生成路径有什么关系。不能把这项监督简写成直接计算 Qwen hidden 或 `U` 与目标特征的逐元素 MSE。

### 5.5 公式与术语保持一致

- 同一个符号在 Overview、模块小节、总损失和结构图中保持相同含义。
- 拼接明确是 token／序列维还是通道维。本项目 `c_m=[G_m(d);U_m]` 为 token 维拼接，不机械照搬 GLARE 的条件通道拼接表述。
- 公式前定义预测、目标和必要的有效范围，公式后只解释新增符号和关键归一化规则。
- `listener media` 可以理解，但当前正文优先使用更具体的 `target listener video and audio`。
- 优先写 Qwen “processes the inputs together with the description”，避免用含义不明的 “We re-encode” 带过计算。
- Event 的 logits 是原始分数；若结构图颜色表示 0–1 概率，标 `Predicted probabilities` 或 `Sigmoid(logits)`。标签是 0/1，未知项另用 mask 表示。详细数值与画法见监督说明文档。

## 6. 正文、Implementation Details 与补充材料如何分工

| 位置 | 应保留的内容 |
|---|---|
| Overview | 任务、总体分工、条件路径、速度预测至媒体输出的过程、两项监督的作用位置 |
| 对应模块小节 | 模块动机、关键输入输出、主要计算路径、公式及必要机制解释 |
| Training and Inference | 总目标、各项职责、参数更新范围、推理条件构建及联合采样流程 |
| Implementation Details | 正式模型版本、训练与采样配置，以及复现所需的核心数值 |
| Supplementary | 完整提示模板、详细 shape、边界 mask 规则、模块内部设置及更多实现／验证说明 |

只要某项维度或参数是理解设计所必需的，就可以保留在主文；其余数值按篇幅后移。避免为了简短而省略关键机制，也避免把缓存、恢复、工程检查的过程日志直接放进方法正文。

以上是内容分工建议，不强制每一行单独成为编号小节。参考论文的小节数服务于它们自己的任务，不需要逐项照搬。

## 8. 后续逐段修订自查

| 检查维度 | 要问的问题 | 当前执行原则 |
|---|---|---|
| 贡献定位 | 是否区分基座能力、继承结构与本文设计？ | LTX 原生联合生成有来源；Whisper 分支不单列为主要贡献 |
| 写作清晰度 | 段首是否点明职责？每句话是否服务于同一段落目的？ | 沿信息流叙述，避免重复 Overview、堆叠模型名和未定义术语 |
| 实验证据 | 机制解释是否被误写成已验证的性能提升？ | 设计目的与实际增益分开写，效果结论对应最终实验 |
| 评价覆盖 | 是否用类别出现代替全部互动质量？ | 行为类别、语境适当性和视听协调分别解释 |
| 方法一致性 | 公式、图、代码版本及训练阶段是否一致？ | 核对 Feature 的预测对象、Event 的整段范围、拼接维度和参数更新归属 |

实际改写一个小节时，先列出该小节的输入、输出、监督依据和用途，再按“动机—计算—目标—机制”写出连续正文。完成后倒着检查每一句是否有明确作用；实现细节和效果结论各自放回合适的位置。
